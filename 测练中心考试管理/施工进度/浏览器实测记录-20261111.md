## 🐛 发现的真实缺陷（3 个，全部已修）

### 缺陷 1：入场页 HTML 注释写法错误 → 整个页面编译失败（**最严重**）

**现象**：点考试卡片无反应，路由停留在列表页。控制台报
`TypeError: Failed to fetch dynamically imported module: .../ExamEntryPage.vue`，
`curl` 该文件返回 **HTTP 500**。

**根因**：模板里的一处注释
```
<!-- 白色卡片：实测宽 1200、圆角 8、上下内边距 40 */
```
**以 `<!--` 开头却用 `*/` 结尾**（CSS 注释写法）。Vue 编译器因此把后续整段模板当注释吞掉，
报 `Invalid end tag.`。

**修复**：改为 `-->` 结尾。

**为什么 `type-check` 和 242 个单测都没发现**：
`vue-tsc --build` 只做**类型检查**，不编译模板语法；
组件单测用 `@vue/test-utils` 的 mount 也不经过 Vite 的 SFC 编译链。
**这是本次施工最大的验收盲区**——所有代码「检查全绿」，但页面根本打不开。

> 教训：`type-check` + 单测通过 ≠ 页面能跑。**必须至少用 dev server 请求一次每个页面**
> （`curl http://localhost:3000/src/views/...` 返回 200 即通过），成本极低但能拦住这类问题。

### 缺陷 2：优秀分数恒为 `--`（后端写死 null）

**现象**：入场页「优秀分数」显示 `--`。

**根因**：`StudentExamServiceImpl` 里 `entry.setExcellentScore(null)` 写死。
注释理由是「本平台没有优秀分数落点」，但**实际管理端表单有**
`publishSettings.excellentScore` / `excellentScoreType`。

**修复**：新增 `resolveExcellentScore()`，读真实配置；
`excellentScoreType=1` 按固定分、`=2` 按比例；配置为 0 或缺失时返回 null（前端显示 `--`）。

### 缺陷 3（数据问题，非代码）：我造的测试数据中文乱码

**现象**：考试名显示 `E2E????`、考生姓名 `?????`。

**根因**：用 PowerShell 传中文给 `mysql.exe` 时被按本地代码页转码，**存进库就是错的**。
前端只是忠实显示，不是前端 bug。

**修复**：改用 hex 字面量写入：
`UPDATE ... SET name = CONVERT(UNHEX('453245E6B58BE8AF95E88083E8AF95') USING utf8mb4)`
（`E2E测试考试` 的 UTF-8 字节序列）。纯 ASCII SQL，彻底绕开命令行编码。

> 造测试数据的正确姿势：**中文一律用 hex 或从文件读入**，不要走 PowerShell 命令行传参。

## 环境问题（非代码）

- **Bash 执行器 `EXECUTOR_UNAVAILABLE`**：dsh-ops 的 exec-tree 并发缺陷，
  每次崩溃叠加 156 条 ACE（DENY）到共享载荷 inode，重试令问题变差。
  - 自行清理：`cd C:\Users\me\.dsh\profiles\desktop\node_modules\dsh-ops && node .\bin\dsh-ops.mjs cache reclaim --yes --all-hosts-stopped`
  - **教训：不要用 `run_in_background` 跑长任务**——后台 job 长期占用执行树是复发主因。
  - 启动服务改用 `Start-Process` 让进程**脱离 bash 进程树**，
    这样 kill 后台 job 不会连带杀掉服务（本次踩过一次，全部服务被连带杀死）。

## 🐛 本轮发现并修复的第 3、4 个缺陷

### 缺陷 3：多空填空题只渲染 1 个输入框（**真 bug，前后端各一处**）

**现象**：题干「面向对象的特征有(_)(_)(_)」只显示 1 个输入框，学员无法填第 2、3 空。

**根因（两处口径分叉）**：
- **后端 `StudentAnswerServiceImpl.blankCountOf`**：只按**换行**切答案，`封装性；继承性；多态性` 是分号分隔 → 得到 1
- **`QuestionGraderImpl.blankCountInContent`**：只认 `_(1)_` 这种**带编号**占位符，`(_)(_)` 无编号 → 返回 0

**修复**：
- `blankCountOf`：分隔符扩展为 `[换行 | 分号（全角半角） | 竖线]`，再兜底数无编号占位符 `(_)`
- `QuestionGraderImpl.splitAnswers`：**同步同一套分隔符**——否则「界面 3 个框、判分只认 1 个空」，学员填了也不得分

> 这类 bug 单测抓不到：`QuestionGraderImplTest` 17 条、`StudentAnswerServiceTest` 21 条全绿，
> 因为它们各自测自己的口径，没人测「两边是否一致」。**必须靠真实数据端到端跑才好发现。**

### 缺陷 4：优秀分数恒为 `--`

已在前面记录（后端写死 null）。修复后显示 `10分`。

# 人脸核验增强：动作式活体（2026-11-12 定稿）

## 为什么不是方案 B（人脸比对）

比对（抓拍与首次建档照片比相似度）看起来更强，但收益被两件事抵消：

1. **首次建档防不住首次替考**（DEF-01）：基准照是学员第一次自己拍的，第一次就可以是别人
2. 要真正防替考，前置条件是**官方基准照**（HR/管理员预录），那是另一个管理端功能

所以本期做动作式活体：成本可控、纯前端、能挡住「对着摄像头举照片/放视频」这类最粗糙的作弊。

## 活体判定状态机落地（task-2，2026-11-12）

产物：`livenessChallenge.ts`（469 行）+ `.spec.ts`（499 行，41 用例）
验证：type-check 通过、单文件 41/41 绿、全量 24 文件/298 用例绿（基线 23/257 未受影响）

### 阈值与理由

| 常量 | 值 | 理由 |
|---|---|---|
| `BLINK_CLOSED_ENTER` | 0.6 | 自然睁眼 0.05~0.3、闭眼 0.7~0.95；0.6 防眯眼被当眨眼 |
| `BLINK_OPEN_ENTER` | 0.3 | 与 0.6 之间留滞回带，带内帧不推进也不清零 |
| `BLINK_CLOSED_FRAMES` | **1** | 见下方裁定 |
| `BLINK_OPEN_FRAMES` | 2 | 确认"睁着"要连续 2 帧（约 500ms） |
| `TURN_YAW_THRESHOLD_RAD` | 0.35 rad ≈ 20° | <15° 自然晃头误判，>30° 容易转出画面 |
| `TURN_YAW_RETURN_RAD` | 0.12 rad ≈ 7° | 噪声约 ±0.05 rad，要求回 0 会永远差一点 |
| `DEFAULT_TIMEOUT_MS` | 15000 | 正常完成 <3s，留找镜头余量 |

**单位假设**：yaw/roll 按**弧度**，blinkLeft/Right 按 **0..1 闭合度**（非布尔）。已写入 `LivenessSample` 的 JSDoc。

### 两处偏离 captain 指示，captain 裁定：采纳

**① `BLINK_CLOSED_FRAMES` 用 1 而非 2~3**

captain 原指示是"连续 2-3 帧 >0.6 视为闭眼"，成员拒绝了。理由更准：
自然眨眼闭眼只有 100~400ms，而检测节拍是 250ms，**一次真眨眼通常只有 1 帧落在闭眼区**。
要求连续 2 帧等于要求闭眼 500ms+，诚实学员会被系统性判失败。
抗抖动改由「滞回带 + 睁眼 2 帧 + 开局基线」承担，不压在闭眼侧。

> **裁决理由**：这是"指示本身有 bug"的典型案例。captain 把抗抖动手段错配到了闭眼侧，
> 成员用物理量（眨眼时长 vs 检测节拍）算出实际命中帧数，比拍脑袋的"2-3 帧"可靠。
> 常量已单独抽出，将来节拍压到 ≤150ms 时改 2 即可，逻辑不用动。

**② 转头方向只进文案、不进判定**

`promptedDirection` 只用于 `challengePrompt()`，判定只看 `|yaw - baseline|`。
理由：human 的 yaw 正负号取决于镜像参数（自拍画面通常水平翻转），
**未真机实测就强制方向，会让一半诚实学员怎么转都判不过**。

> **裁决理由**：看起来严谨（"要求向左转就必须向左"）实则制造 bug。
> 等真机确认镜像口径后加一条方向断言即可收紧，现在收紧是赌博。

### 另两条实现决定（也采纳）

- `faceCount` 校验**排在超时之前**：画面不对时先报「没检测到人脸」比报「超时」更能指导学员
- `faceCount` 为 NaN/缺失时按 no-face 处理，**绝不静默当 1 张脸**

### 给 task-3 的关键约束（成员特别提醒）

`feedSample` 第 3 个参数是**调用方时钟**，必须传 `performance.now()`
（与 `createChallenge` 的 `now` 同一时钟源），**不要传 `Date.now()`**——量纲不同，混用会让 `deadlineAt` 立即失效。

检测循环若 `detectOnce` 抛错，该帧无样本但时限还在走，**必须调 `checkTimeout()` 推进**，否则循环永远卡在 `active`。

### task-2：判定状态机（469 行 + 46 用例）

纯函数、零 import、无时钟调用（时间由调用方传入）。

### ⚠️ 本轮最重要的坑：极性反了

`gesture.ts:65-68` 里 `openLeft = |374y-386y| / |443y-450y|`，变量名叫 **openLeft（睁眼度）**，`< 0.2` 判 blink —— **越小越闭**。
而状态机初版契约写的是 `blinkLeft`（**闭合度**：0=睁 1=闭）。**极性相反。**

后果不是"打点折扣"，而是**诚实学员 100% 超时**：睁眼时 openLeft≈0.6~0.9 → 被判成"闭"；`BLINK_OPEN_ENTER=0.3` 永远不满足 → 永远判不出眨眼。

**连 `1 - openLeft` 这个"修正"也是错的**：task-1 实测睁眼 **openLeft = 0.414**，
`1 - 0.414 = 0.586` 恰好落在旧滞回带 `0.3~0.6` **内部**（既 <0.6 不判闭、又 >0.3 不判睁）
→ `eyesArmed` 永远不成立 → **仍然全员超时**。只是换了个死法。

> 这条由 captain 推理预判、task-1 实测数据坐实。两个成员各自查源码才把真相拼出来，
> **说明 captain 的转述不能当权威**（captain 最初说的"blink 是 0~1 连续值"是错的，human 根本没这字段）。

### 最终方案：不做映射，直接暴露原始 openRatio

| 项 | 决定 |
|---|---|
| 字段 | `openLeft` / `openRight`（睁眼度，**越小越闭**），刻意**不叫** `blinkLeft`（名字会误导下游以为是闭合度） |
| 阈值 | `BLINK_CLOSED_ENTER = 0.2`（直接采用 human 的判据，只把 `<` 放宽成 `<=`）<br>`BLINK_OPEN_ENTER = 0.35`（实测睁眼 0.41，留 0.06 下沿冗余） |
| 滞回带 | 0.2 ~ 0.35 |
| 两眼聚合 | **`max`**（极性变了聚合方向必须跟着变，否则单眼眨会被当合格眨眼） |
| 归一化 | `normalizeRatio` **不再夹到 [0,1]**（openRatio 量纲本就不保证 ≤1，夹了会压缩上沿） |
| 缺失值 | 输出 **NaN 不是 0**（0 会被读成"完全闭眼"＝免费送一次眨眼） |

**为什么这样最稳**：0.2 是 human 作者用真实数据调出来的，比我们拍脑袋可靠；且**零标定风险**——不需要真机采样就能工作。

### 新增的 5 条极性回归测试（专治这次的坑）

第一条就钉死极性：
```ts
it('task-1 实测的睁眼值 0.41 不能被判成闭眼', () => {
  expect(0.41).toBeGreaterThan(BLINK_OPEN_ENTER)   // 0.41 > 0.35 ✅
  expect(0.41).toBeGreaterThan(BLINK_CLOSED_ENTER) // 0.41 > 0.2  ✅
})
```
另覆盖：`<=`/`>=` 写反立刻红、>1 不被夹、单眼眨不算、二值信号只在连续量缺失时兜底。

### 遗留（写进台账，不阻塞）

**`BLINK_OPEN_ENTER=0.35` 架在单点实测（0.41）上**，且该实测来自 human 内置 warmup 样例人脸（正对、光照好、单人），**不是考场 webcam**。
偏差方向是安全的（真机睁眼若漂到 0.35 以下会 arm 不上 → 超时，但我们留了 0.06 余量），
但**真机联调时必须打一行日志看实际 openLeft 分布**，若常态低于 0.35 就下调该常量（改一个数，逻辑不动）。

# 🎯 真机标定（2026-11-12，本轮最重要的验证）

## 数据

用户在考场同类 webcam 上跑诊断页（`public/face-diagnose.html`），**76 帧有效样本、19 次眨眼**：

| `yaw` | 0.045~0.080（几乎正对） |

**两段间隔清晰、无重叠**（0.176 ← → 0.301），信号可用。

## 拦下的致命问题


**如果没做这次真机验证就上线，所有学员都会被误判。** 而这个 bug：
- ✅ type-check 通过
- ✅ 351 个单测全绿
- ✅ 构建成功
- ❌ **真实场景完全不可用**

## 修复

| 常量 | 初版 | 最终 | 依据 |
|---|---|---|---|
| `BLINK_CLOSED_ENTER` | 0.2 | **0.2（不变）** | 实测闭眼 0.176 已低于它，human 原判据成立 |
| `BLINK_OPEN_ENTER` | 0.35 | **0.24** | 实测均值 0.301，留 0.033 余量（诊断页建议 0.25，只留 0.023 偏紧） |

**为什么 `BLINK_CLOSED_ENTER` 不下调**：我原以为要一起改，但数据证明 0.176 < 0.2 已成立。保持 human 原值风险最小。

**偏差方向安全**：`OPEN_ENTER` 偏低只会让「睁眼」更容易成立，**不会让照片通过**——照片永远不会闭眼到 0.176。

## 连带修正：测试夹具用的也是"理想值"

原 spec 里 `EYES_OPEN = 0.41`、`EYES_CLOSED = 0.05`，是 human 样例的极端值。
**用这种夹具测不出阈值定错**——0.41 无论阈值是 0.35 还是 0.24 都能通过。

已改为真机值 `0.301` / `0.176`。这样阈值若再调到不合理高度，测试会立刻红。
滞回带测试也从硬编码 `0.28/0.3` 改成用常量推导，以后调阈值不用改测试。

## 教训（写进方法论）

**"单测全绿"不等于"能用"，尤其当夹具用的是理想值而非真实分布时。**

判定类功能（阈值/分类器/信号处理）必须有一步：**拿真实设备/真实数据跑一遍，看分布落在哪**。
这次是 76 帧真机数据救了 351 个测试都没发现的问题。

成本极低（一个诊断页 + 一次眨眼），收益是避免全员误判。

## 人脸比对三个 bug（2026-11-13）

用户实测发现两轮相反的症状：先「同事能过」，后「本人也过不了」。根因是三个独立缺陷叠加。

### bug 1：比对结果根本没参与判定

```ts
compareOutcome.value = { similarity, compared }   // matched 被丢弃
const outcome = await runVerify(frame)            // 只取活体结果
```

后端 `identity_method=2` 证明比对跑了、相似度也算出来了（0.10 / 0.16），
但这个结论**从未流向 `identity_status`**——活体通过就记 1。所以任何人都能过。

**修**：`matched` 纳入 `FaceCompareOutcome`；`captureAndVerify` 改为
「活体通过 **且**（未比对 或 比对判定同一人）→ pass；比对判否 → fail」。
fail 仍可继续考试（DER-07）。

### bug 2：embedding 压根没算出来

human 的 `description` 默认 `skipFrames: 99` / `skipTime: 3000`（99 帧或 3 秒内复用上次结果）。
我们的用法是**每张图只跑一帧**（基准照是静态图、抓拍也只取一帧），于是每次都命中缓存，
拿到空壳向量：1024 维里只有 567 个非零，距离高达 8.65。

**修**：`description: { skipFrames: 0, skipTime: 0 }`。

### bug 3：阈值 0.6 是从别人数据集抄的

| 项 | 值 |
|---|---|
| faceres 实际向量模长 | **12.374** |
| 同一组真实图片实测距离 | **8.65** |
| 原阈值（抄 human demo / LFW） | 0.6 |

这不是「调参」，是**量纲级错误**：LFW 数据集的向量尺度和 faceres 在考场 webcam 输出上差一个数量级。
用它 = 本人也一律判否（正是用户第二次报的症状）。

**修**：默认值改 **12**（偏宽占位），并加 `resolveThreshold()` 支持
`localStorage['face-match-threshold']` 运行时覆盖，便于现场标定而不必改代码重建。

**偏差方向刻意选安全**：宽了只是少抓替考，紧了会把诚实学员挡在门外。

### 教训

**同一个功能出现两个方向的错误（谁都能过 → 谁都过不了），说明中间有一环根本没接上，而不是参数没调好。**
第一次看到 0.10 的相似度还记通过，就该顺链查「这个数被谁用了」，而不是继续调阈值。

### 数据清理（配合本次修复）

清空前做了盘点，只清人脸相关：
- `exam_face_baseline` 全表清空
- `exam_attempt` 的 `identity_status/method/score/evidence` 四列归零
- 磁盘人脸图片删除（签名图与题目附件未动）

## 阈值标定：从「谁都过不了」到「谁都能过」再到可用（2026-11-13）

### 真实数据（浏览器内实测，两套方法交叉验证）

| 对比 | 欧氏距离 | 相似度 |
|---|---|---|
| **本人** vs 基准照 | **4.532** | 0.1808 |
| **同事** vs 基准照 | **10.145** | 0.0897 |

交叉验证（不依赖 embedding，直接比 32×32 灰度图的 RMS）：
本人 0.0979 / 同事 0.3679 —— 方向一致，说明 embedding 结论可信。
向量模长约 **12.374**，维度 **1024**。

### 合法阈值区间

```
(4.532, 10.145)     ← 阈值必须落在这里
```

取 **8**：距本人 3.47（1.77 倍）、距同事 2.15（1.27 倍），两侧都有余量。

### 两次踩坑（都必须由测试守住）

| 取值 | 依据 | 后果 |
|---|---|---|
| **0.6** | 照抄 human demo / LFW 数据集 | 本人 4.53 被判否 → **谁都过不了** |
| **12** | 只看到「本人被误伤」就一味放宽 | 同事 10.15 也能过 → **谁都能过** |

**关键教训：判断阈值对错不能只看一边。**
必须同时满足 `selfPass` 与 `otherReject`，只优化其中一侧必然走到另一个极端。

单测已改为直接断言这两个性质（`faceMatch.spec.ts`）：
- 阈值 ∈ (4.532, 10.145)
- 两侧余量 > 15%

### 其他两个 bug（与阈值无关，但共同导致现象混乱）

## 结果页考生答案显示成裸 JSON（2026-11-13，DER-35）

### 现象

`GET /api/exam/result` 的 `submitContent` 返回：
```json
{"answer":[],"attach":[]}
```
而不是契约 04 §778 约定的 `"A"`。

### 根因：把「选项 Item ID」当成了「选项下标」

数据库里 `exam_attempt_answer.answer_json` 的真实格式（DER-15 / 03 §10B.5）：
```json
{"answer":["2112444930953543683"],"attach":[]}
```
里面是**选项 Item 的雪花 ID**，不是 A/B/C 下标。

而 `ExamResultServiceImpl.parseAnswer` 只认两种结构：
- `[...]` 数组
- `{"selected":[...]}`

走到 `{"answer":[...]}` 时，`addNode` 拿到的节点是**对象**，
既不是数字也不是文本 → 什么也不加 → `picked` 为空
→ `formatSubmit` 兜底 `return raw` → 前端看到裸 JSON。

### 同一个 bug 的第二个后果（更危险）

第 189 行的 `choiceItems[].checked` 也走 `parseAnswer`：

```java
Set<Integer> picked = parseAnswer(...);
c.setChecked(picked.contains(i));   // 永远 false
```

**「考生选了哪项」在结果页永远显示为未选中。**
这比裸 JSON 更隐蔽——界面上看不出异常，只会让人以为考生没作答。

### 修复

- `parsePickedItemIds(raw)`：正确解析 `{"answer":[...]}`，返回 **Item ID 列表**（字符串）
- `formatSubmit(raw, items)`：用 Item ID 到本题选项列表里查序号 → 转字母
- `choiceItems[].checked`：改成按 Item ID 比对
- 兼容保留：裸数组、纯字母串（导入题 / 人工排查）

### 顺带修掉的一个隐患

非 JSON 输入原先**无条件扫字母**，导致损坏的 JSON（如 `{not valid json`）
会把里面零星字母当成选项，编造出不存在的答案。
现在要求整串全是字母才按字母串解析，否则返回空。

> 这条是写测试时发现的——**先写测试再跑，才能发现这种"看起来无害的兜底分支"**。

### 验证

新增 `ExamResultAnswerParseTest`（8 条），重点守住：
- 真实格式必须解析出 Item ID
- **解析结果里不能出现 `answer` 字段名或 `{`**（出现即说明又把整串 JSON 当答案了）
- 损坏 JSON 返回空而不抛异常（结果页不能因一道题 500）

后端全量 **217 tests，0 failures**。

### bug 3 的排查过程（值得记）

我先试了这些**都无效**：
- 列上 `width` 改 `min-width` → el-table 按比例压缩
- `.table-wrap` 加 `min-width: 0` → 无效
- `:deep(.el-table) { width: max-content }` → 被覆盖
- `flex: none` / `display: block` → 无效

最后用**逐项试验**（改一个样式、量一次 `scrollWidth`）定位到 `max-width: none` 才是解药。
教训：CSS 被框架内联样式压制时，逐个 trial 比读文档快。

### 三态改造（台账 16c7）

`ExamListPage.vue` 的 `hasBaseline` 从 boolean 改为 `'unknown' | 'yes' | 'no'`：

- `unknown`（未查/查询失败）→ **不弹录入框**，只给一条 warning 提示 + 「重试」按钮
- `yes` → 不提示
- `no` → 正常提示并允许录入

**为什么必须三态**：boolean 时接口失败只能二选一——当 `true` 会掩盖「真的没录」（原 7cbc bug），
当 `false` 会在接口挂掉时误报「没录」并弹录入框，学员点进去可能仍失败。
两者都是把「不知道」硬拗成「知道」。
