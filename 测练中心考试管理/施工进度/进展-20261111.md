## 三、captain 本轮修掉的问题

### 1. `FaceVerifyDialog.vue` TS2367（真错误）
TS 赋值收窄：`phase.value = 'checking'` 后判 `!== 'unavailable'` 被判恒真。改用 `[...].includes()` 绕过收窄。

### 2. 人脸核验结果无法落库（**契约缺口，最重要**）
- **现象**：DER-07 的"证据采集"只有前端逻辑。`StartReq` 无 identity 字段，
  `04 §11` 也没有核验接口 → `exam_attempt.identity_status` **永远写不进去**。
- **修复**：新增 `POST /exam/student/attempts/{attemptId}/face-verify`
  - 后端 `FaceVerifyReq` + `StudentExamService.reportFaceVerify`
  - 前端 `reportFaceVerify()`，用 `silent: true`
- **设计取舍**：
  - 独立接口不塞进 `start`——核验与"闸门"语义相反，混入会误导后来人
  - 三种情况都不报错：答卷不存在静默返回 / 状态非法按"无法核验"记 / 图空保留原值
  - 越权（非本人答卷）静默丢弃，不回 403 以免前端流程中断

### 3. 契约与类型冲突
`04 §11.7` 规定答题页返回 `cards[].answer`，但 `types/studentExam.ts` 只有 `userAnswer`。
已补 `answer?: AnswerDraft`，并注明：`answer` 是答题页完整草稿，`userAnswer` 是答卷详情简化数组。

### 4. `Paper` DTO 缺 2 个契约字段（fe-run 发现，2026-11-11 补）
`StudentAnswerRespDtos.Paper` 缺 `name`（考试名）与 `passScore`（通过分数），
导致前端只能隐藏标题行、通过分数显示 `--`，截图上看像前端 bug 实为后端缺字段。

**已补**，赋值在 `StudentAnswerServiceImpl.paper()`：
```java
// 从 arrange 现读而不是快照：这两个是展示属性，考试改名后应显示新名字，
// 与 config_snapshot 冻结的「计时/判分口径」性质不同。
ExamArrange arrange = arrangeMapper.selectById(attempt.getArrangeId());
if (arrange != null) {
    paper.setName(arrange.getName());
    paper.setPassScore(arrange.getPassScore());
}
```

### 5. `Card` 字段核实（澄清 fe-run 的疑问）
`fe-run` 担心填空 `blankCount` 后端没算会退化成 1 个输入框。**已核实：后端有下发**
`StudentAnswerRespDtos.Card.blankCount`，且 `Card.answer` 是完整的 `AnswerDraft`（含 answer/attach/marked）。
因此 `attemptModel.normalizeDrafts` 的双兼容分支可以在 t3 落地确认后清理。

## 五、Bash 环境处置约定（重要）

**根因**（用户咨询确认）：dsh-ops 的 seal 会给共享载荷 inode 加 `Everyone:(DENY)`；
崩溃路径未 unseal → 每崩一次叠 156 条 ACE。**重试会让问题自愈变差**。
17:02–17:30 积累了 3 层后彻底不可用。

**处置**：
1. **同一时间只跑一个会调 bash 的宿主**（最简单，零拷贝）
2. 或让执行树改走复制模式（每次约复制 785 MiB，慢几秒但免疫竞争）

**我的实践**：
- 绝不在 bash 失败后连续重试
- **不用 `run_in_background` 跑长任务**——后台 job 长期占用执行树，是本次复发的直接原因
- 一次命令跑完所有验证，不分多次
- 失败即停手报用户清理
