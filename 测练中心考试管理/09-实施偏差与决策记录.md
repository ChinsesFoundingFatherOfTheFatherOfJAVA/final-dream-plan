## 怎么读这张表

- 「文档原方案」= `01`~`08` 或 `04-接口文档.md` 里写的做法。
- 「最终选定」= 代码里实际生效的做法，**以本节为准**。
- 「类型」：`契约`（影响前后端/跨服务对接）、`实现`（内部做法）、`范围`（做/不做）、`配置`（部署相关）。

| DER-33 | 能力增强 | 人脸基准照录入（不强制） | DEF-01 明确「防不住首次替考」：动作式活体只能证明屏幕前是活人，证明不了是本人 | 学员在**考试列表页**通过非打扰提示条自愿录入一张基准照（`exam_face_baseline`，一学员一张、重录覆盖），存 `/api/exam/files/**`；接口 `GET/POST /api/exam/student/face-baseline`（2026-11-12） | **能力边界必须先说清**：基准照由学员自己拍，**首次就可以是别人**，所以它只能检测「这次与上次不是同一人」，**不是身份认证**，UI 文案不得暗示"已确认本人"。**为什么放考试列表页而不是一登录就弹**：①学员登录是来用平台的，不是来填资料的，一登录就弹会让人以为是病毒或强制采集；②录入是选填，强制弹窗形同变相强制；③提示条能关掉且关了本次不再烦，弹窗只有"确定/取消"两个都是压力。**为什么不做活体动作**：录入阶段本来就是本人在给自己建档，要求眨眼/转头没有意义——真正防"拿照片冒充"的判定发生在考试前那一刻。**不做强制的理由**：强制采集人脸在多数场景需单独告知与同意，且设备/隐私条件不具备时会把正常学员挡在门外。**查询失败静默当"已录入"**：接口挂了不应变成对学员的骚扰，也不该让页面看起来像报错。**后续（第二步，待做）**：考试核验时若存在基准照，用 human 的 `face.embedding` 做 1:1 比对（零额外依赖，该库已有此能力）；届时需给 `identity_status` 补 `identity_method` 区分「只做活体」与「活体+比对」，否则批阅人分不清 `1` 是哪种通过 |

## 关键决策的展开说明

### D-03 通知通道最终形态

```
ExamService（拥有 exam_*）
  └─ 事务内写 exam_change_notice + exam_notice_outbox
  └─ ExamNoticeOutboxWorker（@Scheduled，30s 轮询 + 指数退避）
        └─ Dubbo NotificationPublishService.publish / cancel
              └─ StaffManagement notification 域（拥有 sys_notice_*）
                    ├─ ChannelSenderRegistry → InAppChannelSender（已实现）
                    ├─ PUSH / SMS / EMAIL（预留，未接入时写失败原因）
                    └─ 学员端 HTTP：GET /api/sm/notices、GET .../unread-count、
                                     PUT .../{recipientId}/read、PUT .../read-all
```

要点：

1. **业务服务不写学员端表**，也不维护已读数；`exam_change_notice` 只存"这次变更通知发了什么"。
2. **已读只对站内渠道有意义**；推送是"送达"、短信是"发送成功"。这一点在接入移动端时尤其重要，
   所以 `sys_notice_recipient.read_status` 只在 `channel=IN_APP` 时被业务读取。
3. **移动端接入时的改动面**：加 1 张已有表（`sys_device_token`）的写入接口 + 1 个 `ChannelSender` 实现。
   业务侧与契约侧都不动。
4. **短信是模板报备制**（阿里云/腾讯云签名+模板需预审），届时正文不能像站内那样自由拼装，
   需要引入 `notice_template` + 变量占位符；本期不建该表，避免建了没人用。

### D-02 显示态与存储态分离

| 对外 `status` | 含义 | DB `publish_status` | DB `run_status` |
|---|---|---|---|
| 0 | 未发布 | 0 | 0 |
| 2 | 进行中 | 1 | 1 |
| 3 | 已结束 | 2 | 2 |

### D-09 撤销对学员端的可见性

撤销一次通知会同时做三件事：

1. 通道侧：`sys_notice_event.status=2`；该事件的投递记录 `delivered_status=3`（列表按 `<>3` 过滤，立即不可见）；
   未读的置 `read_status=1`（撤销后不再计入未读数）。
2. 本地：还没投出去的 `exam_notice_outbox.status=3`，worker 只捞 `status=0`，因此不会被补发。
3. 本地：`exam_change_notice.status=3 已撤销`，管理端历史里能看到"发过又撤回"。

## 学员端考试 · 关键决策展开（2026-11-10）

### DER-01 学员端答题页归属：口径反转

**原口径**（`04` §11）：「本模块提供消费接口，不实现答题页；答题页由学员端模块负责。」

**问题**：这条口径造成学员端考试**从未实现**。排查时确认：
- 前端 `views/exam/` 全是管理端，路由均要求 `requiresAdmin`；
- ExamService 无任何学员端接口；
- 但 `exam_attempt`、`exam_attempt_answer`、`exam_arrange_student` 等表都是管理端在用。

**改判**：由本模块实现。理由：
1. 入场/答题/结果/答卷/批阅五个环节共用同一套表，拆模块必然跨服务读写；
2. 判分引擎 `QuestionGrader` 已在本模块；
3. 批阅人与答卷数据同源，拆开会出现状态不一致。

### DER-03 交卷后先给客观题分：有意偏离原平台

原平台交卷后结果页：是否通过 `--`、成绩 `--`、排名 `--`，全部等批阅完成。

**我们改为**：先展示「客观题 4/9 分」，主观题标注「待批阅」；总分/通过/排名仍等批阅完成。

**边界**：这**不改变最终成绩口径**，只是把已知信息提前告知；批阅完成后所有指标照常刷新。
若后续发现学员误解「客观题分=最终分」，需要在结果页明确标注「最终成绩以批阅完成为准」。

### DER-06 为什么考试配置也要快照

已在 `exam_paper_snapshot` 冻结**试卷内容**，但**考试配置**（时长、通过分）是实时读 `exam_arrange` 的。

风险场景：考试 10:00 开始，时长 60 分钟；管理员 10:30 把时长改成 30 分钟 →
进行中的学员剩余时间从 30 分钟骤降到 0，直接被强制交卷。这是不可接受的。

**方案**：`POST /start` 时把 `{limitMinutes, passScore, answerLayout, allowSubmitAllFinish}`
写入 `exam_attempt.config_snapshot`；后续答题与交卷一律读快照，不读实时配置。

**代价**：管理员改配置后，已开始的答卷不生效（需重新开始才生效）。这是正确语义。

### DER-07 人脸核验：从「准入闸门」改为「证据采集」

原平台有「答题前人脸身份核验」开关，但**勘探时未开启实测**，其失败行为无参照。

**设计原则**：核验是**证据采集**，不是准入门槛。

三层结构：
1. **设备检查不阻断**：摄像头不可用只提示，学员可选继续；
2. **结果只记录不判定**：`pass`/`fail`/`error` 全部落库，均放行；
3. **异常标记进批阅链路**：M2 显示「⚠ 身份待核对」，批阅人看抓拍图与原因，必要时走 `status=4 已作废`。

**为什么不新做独立页面**：M1/M2/M3 本来就要做，批阅人本来就要逐份看卷。
挂在批阅动作上等于零新增页面、零新增流程；独立页面会是又一套列表+状态机，而使用者还是同一个人。

**能力边界（DEF-01，必须向用户明示）**：

| 能防 | 防不住 |
|---|---|
| 后续考试换人（已有基准照） | **首次替考**（首次拍照就可能是别人） |
| 有争议时提供当时抓拍证据 | 摄像头故障造成的误判 |

### DER-09 话术/实战训练任务卡：只展示不派发

已核实：
- 话术训练：`StudentProjectController` 直接列项目，无任务分配实体；

## 首轮浏览器实测的三个教训（2026-11-11）

> 本节不是单条偏差，而是「为什么这些缺陷能躲过全部自动化检查」的总结。
> 当天首次对学员端考试做真实浏览器验证，一次性发现 4 个缺陷，其中 3 个是单测/类型检查**结构上抓不到**的。

### 教训一：`type-check` + 单测全绿 ≠ 页面能跑

**DER-28** 的注释写法错误让整页 500，而当时的状态是：
- `npm run type-check` ✅ 通过
- `npm run test` ✅ 22 文件 / 242 用例全绿
- 后端 `mvnw test` ✅ 209 测试通过

原因是两道检查都绕过了模板编译：
- `vue-tsc --build` 只做**类型**检查，不编译 `<template>` 语法
- `@vue/test-utils` 的 `mount()` 直接拿 SFC 对象，不走 Vite 的 SFC 编译链

**结论**：新增/修改 `.vue` 页面后，必须至少用 dev server 请求一次：
```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/src/views/<path>.vue
# 期望 200；500 即模板/脚本编译失败，错误详情在该响应体里
```
成本一次不到 1 秒，能拦住「整页打不开」这类最严重也最容易被绿灯掩盖的问题。

### 教训二：两处各自自洽的口径，合起来可能是错的

**DER-26** 的填空空数：答题页按「答案有几行」算，判分器按「占位符最大编号」算。
各自的单测都在测自己的规则，**没人测「两边对同一道题是否给出同一个数字」**。

**结论**：涉及「同一事实被两处分别推导」的设计（空数、总分、状态、可见性），
要么抽成单一实现（本次 `AnswerViewPolicy` 就是这么做的），
要么加一条**交叉断言测试**：同一份输入，两边结果必须相等。

### 教训三：契约示例不是契约全部

**DER-27** 的优秀分数：契约 `§11.3` 示例写 `excellentScore: null`，
实现者据此认定「本平台没有这个落点」并写死 `null`。但管理端表单**确实有**该字段。

**结论**：契约里的**示例值**只表示「字段可以为 null」，不表示「平台不支持」。
读到 `null` 示例时应反查管理端表单实际写入什么键，而不是直接照抄。
