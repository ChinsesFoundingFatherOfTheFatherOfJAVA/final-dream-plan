# 通用通知通道设计（学生端通知）

> 版本：v1.0 ｜ 日期：2026-10-14  
> 背景：考试变更通知只是第一个使用场景。后续课程、学习任务、证书、角色权限、AI 训练等事件都可能向学员发送通知。  
> 结论：通知不能由 ExamService 私有实现，必须收敛为通用事件通道，供各业务服务发布、由学员端统一读取。

## 1. 设计目标

- 多业务服务可发布通知事件：考试、课程、学习任务、证书、组织变更等。
- 通知接收人可来自多个维度：用户、部门、角色、用户组。
- 通知有统一未读数、列表、已读状态和后续多渠道扩展能力。
- 业务服务只负责“发生了什么”，通知服务负责“发给谁、怎么送达、是否已读”。
- 首发渠道为站内通知；短信、邮件、钉钉/企业微信、IM 作为后续扩展，不在首期实现。

## 2. 服务归属

> **已确认（2026-10-16）**：本期选**过渡方案**——在 StaffManagement 内新增 `notification` 领域包与
> `sys_notice_*` 表，对业务服务暴露 Dubbo `NotificationPublishService`，对学员端暴露
> `GET /api/sm/notices`、`PUT /api/sm/notices/{recipientId}/read`、`GET /api/sm/notices/unread-count`。
> 不新建 `MessageCenter` 微服务；将来量级变大时按"接口不变"原则整体平移。
> 决策与偏差登记见 `09-实施偏差与决策记录.md`（D-03）。

### 推荐：独立 `MessageCenter` 服务

如果计划让通知成为全平台能力，建议新建独立 `MessageCenter`：

- 领域纯粹：事件、接收人、投递、已读、渠道。
- 不与考试、课程、训练任一业务服务耦合。
- 便于后续接 Redis、MQ、定时任务、短信/邮件渠道。

### 过渡方案：StaffManagement 内新增 notification 领域

如果当前阶段不希望新增微服务：

- 在 StaffManagement 中新增 `notification` 领域包与 `sys_notice_*` 表。
- 对业务服务暴露 Dubbo `NotificationPublishService`。
- 对学生端暴露 `GET /api/sm/notices`、`PUT /api/sm/notices/{recipientId}/read`、`GET /api/sm/notices/unread-count`。
- 将来量级变大时按接口不变原则拆到 `MessageCenter`。

无论选哪种，ExamService 都不得保存学员已读状态。

## 3. 数据模型

### 3.1 `notice_event`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | varchar(32) | 事件 ID |
| source_service | varchar(64) | 来源服务：exam/course/training/... |
| event_code | varchar(64) | 事件码：`ARRANGE_CREATED`、`ARRANGE_CHANGED`、`ARRANGE_CANCELED` |
| biz_type | varchar(64) | 业务类型：ARRANGE/COURSE/TASK |
| biz_id | varchar(64) | 业务主键，如 arrangeId |
| title | varchar(200) | 标题快照 |
| content | text | 正文快照 |
| payload_json | text | 事件参数 |
| severity | tinyint | 0 普通，1 重要，2 紧急 |
| channels | varchar(200) | `IN_APP,DINGTALK,SMS...` |
| dedup_key | varchar(128) | 幂等键，唯一 |
| publish_at | datetime | 计划发布时间 |
| expire_at | datetime | 过期时间 |
| created_at | datetime | 创建时间 |

### 3.2 `notice_recipient`

> **实现补充（2026-10-16）**：实际落库为 `sys_notice_recipient`，并把
> `title / content / source_service / biz_type / biz_id` **冗余**进来。
> 原因：本工程持久层铁律禁止跨表 JOIN，学员端列表/未读数/已读必须单表完成。
> 见 `09-实施偏差与决策记录.md`（D-05）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | varchar(32) | 接收人记录 ID |
| event_id | varchar(32) | 通知事件 ID |
| user_id | varchar(32) | 接收人 |
| channel | varchar(32) | IN_APP/DINGTALK/SMS/EMAIL |
| delivered_status | tinyint | 0 待送，1 成功，2 失败 |
| read_status | tinyint | 0 未读，1 已读 |
| read_at | datetime | 已读时间 |
| delivered_at | datetime | 送达时间 |
| failure_reason | varchar(1000) | 失败原因 |
| created_at | datetime | 创建时间 |

唯一键：`(event_id, user_id, channel)`。

### 3.3 可选 `notice_template`

只用于后续统一模板管理，首期考试通知仍由 ExamService 组装标题和正文快照，不依赖模板表。

## 4. Dubbo 契约

```java
public interface NotificationPublishService {

    NotificationPublishResult publish(NotificationPublishCmd cmd);

    void cancel(CancelNotificationCmd cmd);
}
```

`NotificationPublishCmd`：

```text
sourceService
eventCode
bizType
bizId
dedupKey
title
content
payloadJson
severity
channels
publishAt
expireAt
recipientRule
```

`recipientRule`：

```json
{
  "type": "USER_IDS | DEPT_CODES | ROLE_CODES | ALL",
  "values": ["..."],
  "includeChildDept": true
}
```

接收人解析：

- `USER_IDS`：直接接收。
- `DEPT_CODES`：通知服务调用 StaffManagement 部门树/用户查询，支持含子部门。
- `ROLE_CODES`：通知服务按角色查用户。
- `ALL`：只允许超级管理员或平台运营事件使用，普通业务服务默认禁止。

> **实现补充（2026-10-16）**：首期**不启用**上表的接收人解析，改由业务服务解析好后经
> `NotificationPublishCmd.recipientUserIds` 直接传入。原因：考试变更通知的收件人是
> "本场已安排考生"，属 ExamService 领域数据；通知中心去查 `exam_arrange_student` 即跨域读表。
> `recipientRuleJson` 字段已预留，接入 `DEPT_CODES / ROLE_CODES / ALL` 时无需改契约。
> 见 `09-实施偏差与决策记录.md`（D-04）。

## 5. 学生端 HTTP 契约

### 5.1 未读数

`GET /api/sm/notices/unread-count`

```json
{ "code": 0, "message": "success", "data": { "count": 3 } }
```

### 5.2 列表

`GET /api/sm/notices?readStatus=0&sourceService=exam&current=1&limit=20`

返回统一 `ApiResponse` + `{list,total,page,size}`（本域属 StaffManagement，用 `PageVo`；与 ExamService 的 `PageResult{records,total}` 是两套并存形状，见 `09-实施偏差与决策记录.md` D-01，不要统一）。

### 5.3 已读

`PUT /api/sm/notices/{recipientId}/read`

只能把自己当前用户的 `notice_recipient.read_status` 置为 1。

### 5.4 批量已读

`PUT /api/sm/notices/read-all`

可选，按 sourceService 或全部未读。

## 6. 业务服务集成方式

### 6.1 考试模块

ExamService 保留：

- `exam_change_notice`：管理端“这次变更通知发了什么”的业务记录。
- `exam_notice_outbox`：事务内可靠投递记录。
- 发送流程：

```text
业务事务：
  1. 更新考试配置
  2. 写 exam_change_notice
  3. 写 exam_notice_outbox
事务提交
Outbox worker：
  4. 调 NotificationPublishService.publish
  5. 成功 -> outbox.status=1
  6. 失败 -> status=2, retry_count++, next_retry_at
```

### 6.2 其他服务

任何服务都可按相同方式调用通用通知服务。业务服务不写 student-side 表，不自己维护未读数。

## 7. 去重与幂等

- `dedupKey` 是必填字段。
- 推荐格式：`<sourceService>:<eventCode>:<bizId>:<receiverBatch>`。
- 通知服务用 `dedup_key` 唯一索引防重复发送。
- 重试不会产生重复通知，渠道层再次投递时也按 recipient 唯一键去重。
