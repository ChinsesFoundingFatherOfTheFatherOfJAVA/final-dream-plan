# 学员端考试 · 技术难点与开源方案

> 用途：对「本期都做」的两项高成本能力（人脸核验、AI 智能批阅）给出可选方案，
> 供讨论决策。所有候选均核实过仓库元数据（星数/语言/许可/最后提交），非凭印象推荐。
> 数据抓取时间：2026-11-10。

> ## ⚠ 2026-11-12 最终结论（覆盖下文调研）
>
> 本文是**早期调研记录**，保留供追溯。**最终选型不是 CompreFace**，而是：
>
> **活体检测 + 后续比对统一用 `@vladmandic/human`**（MIT、零依赖、纯前端）。
>
> 选它的四个理由：
> 1. **零额外服务**：CompreFace 要 Docker 部署，human 纯前端、部署成本为零。
> 2. **模型可本地托管**（`public/models/`，约 2.1MB），不依赖外网 CDN。
> 3. **一个库盖完两个需求**：已含 face detection / landmarks / iris / **embedding**，
>    活体和 1:1 比对不用拼两套技术栈。
> 4. **CompreFace 无活体检测**，即使选它仍要另外找个活体方案，反而多一层。
>
> 已实现：动作式活体（DER-32）、基准照自愿录入（DER-33）。待做：基于 `face.embedding` 的 1:1 比对。
>
> **能力边界不变**：活体只能证明「屏幕前是活人」；基准照由学员自己拍，
> 首次仍可能是别人，所以只能检测「换了人」，**不是身份认证**。

## 难点 1：答题前人脸身份核验

### 原平台是怎样的（语义）
入场前拍一张，与**学员档案照**做 1:1 比对，判定是否本人。属于「防替考」。

### 我们的现状
- **没有人脸能力**，也没有学员证件照/头像库。
- 但有文件存储（SpeechTraining `FileStorageService`、ExamService `/exam/files/**`）。
- 需要解决两件事：① 人脸比对引擎；② **基准照从哪来**。

### 候选方案

| 方案 | 说明 | 星数 | 语言 | 许可 | 最后提交 | 评价 |
|---|---|---|---|---|---|---|
| **CompreFace**（exadel-inc） | Docker 部署、REST API、**原生支持 face verification（1:1）**、基于 InsightFace/FaceNet、CPU/GPU 均可 | **8412** | **Java** | Apache-2.0 | 2024-10 | **首选**。Java 生态与我方一致；fork 1192、issue 活跃；缺点：近两年无新提交，且**无活体检测** |
| Faceplugin Open-Source-Face-Recognition-SDK | 含识别/活体/防伪/比对/姿态 | 3146 | — | 需核实 | — | 功能最全，但偏 SDK 商用引流，需核实免费范围 |
| juan-csv/face_liveness_detection-Anti-spoofing | 纯活体（要求做眨眼/转头等动作） | 308 | Python | MIT | 2023-03 | 只解决活体，需与比对引擎组合 |

### 关键判断
1. **CompreFace 能满足 1:1 核验**，且是 Java + Docker，接入成本最低。
2. **活体检测是缺口**。原平台的「答题前人脸身份核验」是否要求活体，勘探时**没观察到**（我们没开这个开关跑过）。若只做「拍照比对」，CompreFace 够用；若要求防照片攻击，需叠加活体方案。
3. **基准照来源是真问题**：我方目前没有学员人脸库。可选：
   - a) 首次核验时**建档**（学员自己拍一张存为基准）——最省，但首次防不了替考；
   - b) 由管理员/HR 预录——要新增管理端功能；
   - c) **本期先不做人脸核验**，用「考前声明确认 + 签名」替代。

### 建议
- 方案：CompreFace（Docker 起一个服务，ExamService 用 HTTP 调） + 方案 a（首次建档）。
- **用户已裁定（2026-11-10）：按首次建档做，接受「防不住替考」这个能力上限，记入契约作为已知缺陷，后续再想办法。**

### 已确认的能力边界（要写进契约）

| 项 | 结论 | 处理 |
|---|---|---|
| 学员人脸库 | **没有**，用户手上也没有学员照片 | 首次核验时建档：学员自己拍一张存为基准 |
| 首次替考 | **防不住**——首次拍照时就可能是别人 | 记为契约已知缺陷（DEF-01），不是实现 bug |
| 活体检测（防照片攻击） | 勘探未观察到原平台是否要求，本期**不实现** | 记为契约待确认项（TBD-01） |
| 人脸比对引擎 | CompreFace（Java/Apache-2.0/8412★），原生 1:1 核验 | 本期采用；注意它无活体能力 |
| 学生档案照预录 | 需要新增管理端功能 | **本期不做**，作为后续防替考的方向 |

> 也就是说：本期人脸核验的实际防护级别 = **能发现「后续考试换人」，但无法发现「第一次考试就是别人」**。
> 契约里必须如实写明，避免上线后被误认为能完全防替考。

## 难点 2：问答题 AI 智能批阅

### 先厘清概念：这是两个层级的配置，不是一回事

| 配置项 | 层级 | 语义 |
|---|---|---|
| 填空题自动批阅 `grading.autoGradeFill` | 要不要自动 | 开=填空自动出分；关=转人工 |
| 问答题自动批阅 `grading.autoGradeQa` | 要不要自动 | 同上，针对问答 |
| 用户未作答不自动批阅 `grading.autoGradeUnanswered` | 要不要自动 | 空答不进批阅队列 |
| **允许问答题智能批阅 `grading.aiGradeQa`** | **怎么自动** | 在「自动批阅已开启」前提下选择判定手段：关=**关键词规则**判定；开=**AI 语义**判定 |

**组合关系（用户已确认按此写契约）**：

```
问答题自动批阅 = 关   → 无论智能批阅开关如何，一律转人工批阅
问答题自动批阅 = 开
    ├─ 智能批阅 = 开 → 调 LLM 按「参考答案 + 关键点 + 评分量规」判分
    └─ 智能批阅 = 关 → 走关键词命中比例判分（现有 QuestionGrader 已实现）
```

> 说明：该层级关系为**推断**（勘探时未做四象限组合实测），用户已确认按此实现。
> 若后续原平台实测与推断不符，需回来修订本节与契约。

### 原平台是怎样的（语义）
配置里有「允许问答题智能批阅」开关。开启且自动批阅开启时，主观题由 AI 判分，无需人工。

### 我们的现状
- **已有 `QuestionGrader`**：问答题按**关键词命中比例**判分，不调模型 ← 即上面的「智能批阅=关」分支。
- 关键词方式的问题：学员同义表达不得分，容易误判。
- 但优势是：**可复现、零成本、无延迟**。

### 候选方案

| 方案 | 说明 | 星数 | 语言 | 许可 | 最后提交 | 评价 |
|---|---|---|---|---|---|---|
| **沿用现有关键词判分** | 已实现，即「智能批阅=关」 | — | Java | — | 本会话 | **零成本**，但严格 |
| Prometheus（prometheus-eval） | 专为「按自定义评分量规打分」训练的开源评估模型（ICLR 2024） | 327 | Python | MIT | 2023-11 | 学术认可、可复现；但需自部署模型，资源成本高 |
| AutoSCORE | 多智能体 LLM 结构化评分（AAAI EAAI 论文） | 4 | Python | MIT | 2026-05 | 思路最新，但仅 4 星，工程成熟度低，不宜直接依赖 |
| 自研 Prompt + 现有 LLM | 用我们已有的 Qwen 通道，把「参考答案+评分量规」喂给模型打分 | — | Java | — | — | **最务实**：无需新服务，复用 `WorkflowLlm` |

### 关键判断
1. **不建议引入 Prometheus/AutoSCORE 部署**：都是 Python 模型服务，与我方 Java 栈异构，且增加运维。
2. **最务实是自研 Prompt**：我们已有 AIGentService 的 `WorkflowLlm.structured` 与 schema 能力，
   用「参考答案 + 关键词 + 评分量规」让模型输出 `{score, reason}`，并用 schema 约束。
3. **可信度处理（待用户裁定）**：AI 判分用于成绩场景有争议，两种口径：
   - **A. AI 只出建议分**：落 `correct_flag=3 待批阅`，人工确认后才生效（更稳，但没省人力）；
   - **B. AI 直接定分**：真省人力，但学员申诉时无法解释判定依据。
4. **风险提示**：一旦 AI 直接决定成绩，申诉场景无解释力。这是建议选 A 的核心理由。


### 建议
- 本期：**AI 批阅做「建议分 + 人工确认」**，不直接定成绩。
- 不引入第三方模型服务，用现有 Qwen 通道 + schema 约束。
- 若你要求「AI 直接定分」，需要接受不可解释性与申诉风险，我会在契约里写明。

## 难点 3：考前/考后签名（非技术难点，但需确认存储）

- 原平台：canvas 手写 → 导 PNG → 上传 → 答卷关联 `signId`。
- 我方：可直接复用 ExamService 的 `/exam/files/**` 存储。
- 唯一决策：签名图**存在答卷表还是文件表**。建议存文件表 + 答卷存 fileId（与原平台一致）。
