## 1. D1 口型驱动：模块化组合 + 发布时预生成

### 1.1 为什么否决全流程整合路线

Linly-Talker / LingCast / LiveTalking / OpenTalking 这类"全流程"方案自带 ASR + LLM + TTS + 数字人渲染整条链路，引入即意味着：

| 代价 | 说明 |
|------|------|
| **替换百炼 TTS** | 已验证的 CosyVoice 音色、语速映射（speech_rate 公式）、TTS 哈希缓存、Mp3Duration 时长解析全部作废，音色一致性丢失，学员听到的陪练者"变声" |
| **替换判定链路** | 陪练者台词来自 `node.trainer_question`（静态）、判定走 Dify 流转评分器，与全流程引擎的运行时对话模型是两套世界观，等于重做陪练引擎 |
| **换来的能力用不上** | 全流程方案的核心卖点是**运行时实时驱动**（学员说一句、数字人实时回一句）。本项目台词 100% 静态（09 §F31 已确认），发布时就知道陪练者要说的每一句话 |

**静态台词是决定性事实**：口型视频可以在**发布时离线生成**，训练时前端只是播视频，运行时零 GPU、零额外延迟。

### 1.2 唇形同步模型选型（模块化路线内部）

保留百炼 TTS 音频，只引入"照片 + 音频 → 说话视频"的唇形同步模型：

| 候选 | 驱动输入 | 质量 | 速度 | 判断 |
|------|----------|------|------|------|
| **Wav2Lip** | 照片 + 音频 | 嘴部 96×96 分辨率，朴素但稳定 | 极快，CPU 也能跑 | **选定：打底跑通链路**，效果不足再升级 |
| **SadTalker** | 照片 + 音频 | 头部姿态微动自然、嘴形更细腻，照片级形象效果好 | 慢于 Wav2Lip（GPU 秒级~十秒级/条） | **选定：质量目标**，Wav2Lip 效果不满意后切换 |
| MuseTalk | 视频/照片 + 音频 | 好 | 可实时 | 实时能力用不上，效果相对 SadTalker 无决定性优势 |
| LivePortrait | 需**驱动视频**（表情/姿态参考） | 极好 | 快 | 输入形态不匹配（我们只有音频），需先造驱动视频，链路变长，不选 |
| HunyuanVideo-Avatar | 照片 + 音频 | 最好 | 极慢、显存要求高 | 太重，内部部署不值当，不选 |

**决策**：部署一个可切换模型的独立唇形服务（§1.4），首发模型 `wav2lip`，配置项可切 `sadtalker`。两个模型的服务契约完全一致，切换只改配置。

### 1.3 预生成链路设计（后端）

#### 1.3.1 触发时机与生成单元

- **触发**：项目发布（`TrainingProjectServiceImpl` 置 `status=1` 的既有校验之后）——这正是 09 §F32 推迟的"重发布钩子"，本方案补上。
- **生成单元**：流程内所有陪练者台词（各节点 `trainer_question`，含开始节点首句）× 该项目 virtual_trainer 配置，一条台词一段视频。
- **缓存键**：`md5(text + "|" + voiceId + "|" + speed + "|" + avatarImage + "|" + model)`。
  四要素任一变化（改文案/换音色/调语速/换形象图）或升级唇形模型，key 自然变化 → 重生成，**这就是重发布钩子的实现原理**：不是 diff 事件，而是"发布时按当前配置算 key，表里没有就生成"。内容相同的两个节点共享同一段视频（key 相同）。

#### 1.3.2 新表 `trainer_video_asset`（DDL 见 07 ⑤）

| 列 | 说明 |
|----|------|
| `asset_key` (CHAR(32), UNIQUE) | 上文 md5 缓存键 |
| `text` / `voice_id` / `speed` / `avatar_image` / `model` | 冗余存生成要素（排查用，不参与逻辑） |
| `status` | 0=待生成 / 1=生成中 / 2=成功 / 3=失败（可重试） |
| `file_path` | 成功后为 `/video/lip/{asset_key}.mp4` |
| `duration_ms` | 视频时长（与 TTS `durationMs` 同源，供前端预加载） |
| `error_msg` | 失败原因（形象图非人脸、服务超时等） |
| `created_at` / `updated_at` | updated_at 由 DB 写（卡死扫描同款时钟纪律，见 09 §K45） |

不加 `(project_id, node_id)` 外键关联——同一台词跨项目复用（key 相同即同一段视频），资产表对项目无感。

#### 1.3.3 生成流程（异步、失败降级、不阻塞发布）

```
发布(status=1) 校验通过
  └─ afterCommit 异步任务（专用线程池 lipsyncExecutor，不复用 reportExecutor）
       ├─ 遍历项目全部节点台词，按当前 trainer 配置算 key 去重
       ├─ 逐条：查 trainer_video_asset
       │    ├─ status=2 → 跳过（缓存命中，重发布不改动的台词零成本）
       │    └─ 无记录/失败 → ① 确保 TTS 音频存在（复用 TTS 哈希缓存，命中则直接拿文件）
       │                      ② 置 status=1 → 调唇形服务(§1.4) → 落盘 mp4 → status=2
       │                      ③ 失败 → status=3 + error_msg，**不抛错、不阻断其余台词**
       └─ 结束。发布接口本身早已返回，管理员无感知（失败日志 + 表状态可查）
```

- **降级原则**：视频是体验增强项，任何失败只影响"该条台词播视频"，训练功能不受影响——学员端拿不到 videoUrl 时播音频 + 静态图（即现状）。
- **重试**：status=3 的行在下一次发布时自动重试；另提供管理端手动触发（本期可只做接口不做界面，见 10 号文档任务说明）。
- **孤儿文件清理**：`/video/lip/` 下的 mp4 与 `trainer_video_asset` 行一一对应；形像/文案改版后旧 key 的文件不再被引用但无害。清理策略：定期（如每周）删除 `updated_at` 超过 90 天且不被任何已发布项目 key 引用的行与文件——本期只记策略不做任务，磁盘预算见 §1.6。

#### 1.3.4 运行时下发（训练时零 GPU）

`POST /student/sessions/{sessionId}/tts`（03 §5.1）响应**新增 `videoUrl` 字段（可空）**：

- 后端按该消息文本 + 会话项目 trainer 配置算 key → `trainer_video_asset.status=2` 且文件存在 → 返回 `/video/lip/{key}.mp4`（相对路径，同 audioUrl 口径，前端 `resolveAssetUrl()` 拼接；后端注册 `/video/**` 与 `/api/video/**` 两套静态映射，同 03 §5.3 avatar 的做法）；
- 否则 `videoUrl: null`，前端走现状（audioUrl + 静态图）。
- `speech.lipsync.enabled=false`（默认）时恒返回 null，功能整体关闭开关。

### 1.4 唇形服务（独立 Python 服务，不进 Java 进程）

```
POST /generate          （同步调用，单条超时 120s）
  请求: { "model": "wav2lip", "image_path": "/avatar/xxx.png", "audio_path": "/audio/tts/xxx.mp3" }
  响应: { "video_path": "/video/lip/tmp/xxx.mp4", "duration_ms": 3200 }
  失败: 4xx/5xx + { "error": "no_face_detected" | "timeout" | ... }
GET /health
```

- 形态：FastAPI + 模型推理，部署在**有 GPU 的机器**（见 §1.5 前置条件）。与 Java 后端通过**共享文件路径**交换音频/图片/视频（同一台机器挂载或 NFS；无法共享时改为 base64 传参，二选一在实施时按部署拓扑定，接口契约不变）。
- 模型切换：请求体带 `model` 字段，服务内路由到对应推理管线；Java 侧 `speech.lipsync.model` 配置透传。
- Spring 侧新增 `service/LipSyncService`：HTTP 调用 + 超时 + 错误分类（`no_face_detected` → 该形象图永久不适用，直接置 status=3 并在 error_msg 标注"形象图不适合驱动，请更换正脸照片"）。

### 1.5 前置条件（实施前必须确认，不满足则 S3 整体推迟；2026-09-24 更新）

| # | 条件 | 现状 |
|---|------|------|
| P1 | **GPU 资源**：Wav2Lip 约 4GB 显存（CPU 亦可但慢），SadTalker 约 8~12GB | ~~待确认机房余量~~ **两条路已排除**：用户无 10.10.166.81 权限；本机为 Iris Xe 核显（共享显存、无 CUDA，PyTorch 链路不可用）。**新路线：PoC 用本机 CPU 跑 Wav2Lip（只验效果不追速度）；生产走云上按需租卡**（发布时起实例、跑完释放；Wav2Lip 入门卡几元/小时，SadTalker 升 8~12GB 规格）。§1.4 唇形服务是独立 HTTP 服务，`speech.lipsync.base-url` 指向云上实例即可，架构零改动。按条计费的 D-ID/HeyGen 类 API 为保底（成本随条数线性涨、数据出内网、风格不受控），非首选 |

### 1.6 前端改造（TrainChat.vue + ScriptTraining.vue）

- 形象卡（280×280，FP-27）由 `<img>` 改为 `<video>` 为主、`<img>` 兜底：
  - `poster` = `trainerFace(avatar)`（现有单一来源函数，静态帧与视频首帧同脸）；
  - 收到陪练者消息 → 调 `/tts`：`videoUrl` 非空 → `<video :src>` 加载并 `play()`（播完停在最后一帧，下一条消息到来重新播）；`videoUrl` 为空 → 隐藏 video、显示 img + 播 audio（现状行为，一行逻辑分叉）；
  - **单槽纪律不变**（09 #14）：播放陪练者视频/音频前 `player.stop()`，学员回放自己的录音仍会打断播报——一对一对话里"同时只有一个人在说话"。
- 气泡 🔊 重播：**维持播音频**，不再播视频（视频挂在形象卡，气泡重播是快速回听语义，不需要画面）。
- 自动播报仍限 `dialogueMode=0` 项目（03 §5.1 既有口径不变）。
- 静态资源注册：`/video/**` 静态映射 + `resolveAssetUrl` 无需扩展（同前缀规则）。

### 1.7 风险与对策

| 风险 | 对策 |
|------|------|
| 形象图不适合驱动（侧脸/遮挡/AI 生成畸变） | 生成时服务返回 `no_face_detected` → status=3 + 明确 error_msg；**不影响训练**（降级音频）。生图主路径（1024×1024 正脸写实人像）天然适配，风险集中在"本地上传"路径 |
| 发布时批量生成耗时（SadTalker 慢 × 节点多） | 异步不阻塞发布；逐条独立成功/失败；量大时唇形服务可并发（服务侧限流） |
| 视频存储增长 | 每条约 1~3MB；缓存键天然去重（同台词同配置全项目复用）；90 天清理策略（§1.3.3） |
| 唇形服务不可用 | `enabled` 开关一键关闭；运行时查不到 status=2 即降级，训练永不因视频失败 |

## 2. D2 语气维度：Qwen2-Audio 两阶段

### 2.1 现状与思路（2026-09-24 路线微调：PoC 改调百炼 API，自建降为备选）

- "语气/热情/亲和/自信"本质是**韵律特征**（音调起伏、能量、节奏风格），豆包 SAUC 不返回情感/韵律标签，纯代码算不了；
- 让 Dify 按转写文本"近似评语气"已被否决——没有声学信号就是猜，等于重蹈"纯文字轮语速分幻觉"（09 #8）的覆辙；
- **数据侧已就绪**：原始录音按 messageId 落盘（`/audio/asr/{id}.wav`，含撤回答案）、逐字时间戳留存（`training_round_acoustic`），离线可验证、验证通过可无缝入链路——这就是先 PoC 的底气。
- **部署路线（2026-09-24 确认）**：Qwen2-Audio **优先走阿里云百炼音频理解 API**（qwen-audio / qwen2-audio-instruct，OpenAI 兼容）——dashscope key 与 TTS 同源现成、零 GPU、零新增供应商、按量计费（PoC 30 样本成本可忽略）；自建 vllm 降为备选（仅当 API 效果不足且怀疑是部署因素时）。用户无 10.10.166.81 服务器权限，本机为 Iris Xe 核显（无 CUDA、共享显存），自建路线在本工作区不可达。

### 2.2 Phase 1：PoC（不改任何生产代码）

- **部署（2026-09-24 起）**：调**百炼 qwen-audio 系列 API**（DashScope OpenAI 兼容接口，audio 输入；key 复用 TTS 的 dashscope.api-key），不部署任何模型。原"vllm 起 Qwen2-Audio-7B-Instruct"的自建方案降为备选。
- **评分协议（提示词，PoC 版）**：

  > 你是话术训练的语音表现评审。听这段学员录音（附 ASR 转写文本：{text}），从"{aspect}"角度给 0-100 分并说明依据。锚点：100=该角度表现突出、有感染力；80=良好；60=合格、平淡；40=明显不足；0=完全背离。只输出 JSON：{"score": N, "reason": "一句话依据，引用录音中可听到的具体表现"}。
  >
  > aspect ∈ {热情, 亲和, 自信}（单次调用评一个角度，避免多任务互相污染）。

- **样本**：现有 11 条留存录音起步，补采 20~30 条真实对练（不同状态的：有感情的/念稿的/紧张的）。
- **验收标准（go/no-go，人肉评审）**：
  1. **区分度**：样本分数分布不挤在 70-80 一带（极差 ≥ 25 分）；
  2. **稳定性**：同一条录音重复评两次，分差 ≤ 10；
  3. **方向正确**：评审人预判"明显好/明显差"的样本，模型打分方向不反（好样本 > 差样本）。
- **产出**：PoC 结论（go → 进 Phase 2；no-go → 语气维度继续"不评"，回到攒数据状态，不硬上）。

### 2.3 Phase 2：`tone` 指标入链路（复用现有架构，零新概念）

PoC 通过后：

- **白名单**：`DimensionMetricConfig` 增加 `tone`；`metric_config` 形态 `{"metric":"tone","params":{"aspect":"热情"}}`——**aspect 是参数**，同一个指标服务"热情/亲和/自信"任意自定义语气维度。
- **管理端**：定分方式下拉增加"音频模型评语气"；选中后出现"评什么角度"输入框（默认"热情"，2~6 字），提交 `metricKey="tone"` + `metricAspect`（03 §5.4b 同步扩展）。
- **后端**：新增 `service/ToneScoringService`：报告生成时，对**进入评分的语音轮**（通过且未撤回，与 `roundSpeeds` 同口径）逐条调音频模型，按轮次字数加权平均得维度分 → 走既有"后端已判定"管道（rule 标注注入 + measured 覆盖双保险，09 #9 机制原样复用），Dify 只写评语。
- **失败降级**：音频模型超时/失败 → 该维度**不参与评分**（`score=null` + 原因文案，同 `NO_ACOUSTIC_REASON` 口径），**绝不编造分数**——与 09 #11 的纪律一致。
- **时效预算**：报告生成本就是异步（60s 预算），N 轮并发调用（每条 2~5s）在预算内；轮数 > 20 时限流并发防雪崩。

## 3. D3 语速口径：切换为净发声时长 speech_ms

### 3.1 变更内容

- `ReportGenerationService#buildRounds`：`input_mode=2` 的轮次，`speech_speed` 改为 `字数 ÷ speechMs × 60`（speechMs 取 `training_round_acoustic.speech_ms`，**按 message_id 批量查表**）；
- **回落链**：`speech_ms` 为 null 或 ≤ 0（DDL 之前的两条老消息、解析异常）→ 回落 `msg.audioDurationMs`（含停顿的旧口径），日志 WARN 一次；
- 下发给 Dify 的 `speech_speed`、`SpeechSpeedCalculator` 公式（区间/扣分）**均不变**，变的只是分子分母里的时长来源；
- 满分区间参数化（`params.bestMin/bestMax`）已存在，本次不受影响。

### 3.2 语义声明（写进维度默认规则文案）

- 切换后**"语速适中"不再惩罚长停顿**：学员慢慢说但说得流利，语速分不再被拖低；
- 停顿数据（pause_count / pause_total_ms / max_pause_ms）**保留给"表达流利"类混合维度**（§4 声学注入使用），两个维度各管各的、不互相污染——这是本次决策的明确取舍，不是遗漏。
- 历史报告不重算（口径变更只对新报告生效）；老消息缺 acoustic 行时自动回落旧口径，无需迁移。

### 3.3 单测

- `SpeechSpeedCalculatorTest` 补：speech_ms 存在时优先、为 null 回落 audio_duration_ms、≤0 回落，三例。

## 4. D4 混合维度：声学摘要注入提示词

### 4.1 注入内容与格式

`evidence_type=3`（文字+语音）的维度参与评分时，`toDimensionsJson` 在其 rule 文本后追加（格式与"后端已判定"标注同风格，括号注入）：

```
（语音表现参考——评分时请结合使用，但不要只按它打分：第1轮 语速192字/分、停顿1次共2.3秒；第2轮 语速205字/分、无停顿记录；…）
```

- 数据源：`rounds` 里的 `speech_speed`（§3 切换后即净发声口径）+ `training_round_acoustic` 的 pause 字段；**只有语音轮出声学条目，文字轮不出**；
- 会话全部为文字轮时**不注入**（没有事实就不给参考，防止模型对"无数据"脑补）；
- 与"后端已判定"标注互斥：定分维度（metric 非空）不注入声学摘要——它们已有确定分数，不需要模型再参考。

### 4.2 Dify 提示词升级（04 yaml 同步修订）

system prompt 在第 5 条（后端已定分）之后新增：

```
6. **带"语音表现参考"标注的维度（不区分维度名称）**：若某维度的 rule 里带有"（语音表现参考——…）"，
   说明该维度要综合文字内容与语音数据（语速、停顿）评分：文字仍是主要依据，语音数据用于佐证与调节分档
   （如"表达流利"维度：多轮长停顿应在评语中指出并酌情降档；语速平稳、停顿少可支持高分）。
   注意：语音数据只是参考输入，不是公式——不要机械地按"语速多少必须扣多少分"打分；
   没有"语音表现参考"标注时，按文字正常评，不得虚构语音表现。
```

- 这一条同时关闭 FP-25 ⚠️ 标注的"提示词未要求使用语速/时长字段"欠账（01/02 同步修订见 §6）。

## 8. 本方案的"不做"清单（与 01 附录A 同纪律）

| 项 | 不做原因 |
|----|----------|
| 实时唇形驱动（流式） | 台词静态，预生成已覆盖全部需求；实时链路引入 GPU 常驻与延迟预算问题，收益为零 |

| 视频抠像/背景替换 | 形象卡 1:1 展示与原视频比例一致，无需处理 |
