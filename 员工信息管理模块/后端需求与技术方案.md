> 版本：v1.1（2026-09-23）

## 一、需求概述

### 1.1 功能范围

| # | 能力 | 交付形态 |
|---|------|---------|
| 1 | 按名称模糊查询员工（中文姓名 / 英文姓名 / 工号） | Web 接口 + Dubbo 方法 |
| 2 | 查询指定部门及其**全部下级部门**的员工，并体现下级部门的层级关系 | Web 接口 + Dubbo 方法 |
| 3 | service 层以 Dubbo 服务提供者形式暴露，供其他应用后续消费 | `@DubboService` |

### 1.2 明确不做（本期边界）

- 不做增删改：视图只读，且视图背后是 SHR 主数据，写回没有落点。
- 不做登录鉴权与数据权限：先做成普通 Web 应用，权限由网关侧或调用方自行控制。
- 不做前端页面：只提供接口。
- 不做员工全量导出：视图单次全量扫描实测 5.8~6.0 秒（34173 行），导出走异步任务另行设计，不塞进查询接口。
- 不建自己的员工表：所有数据实时来自视图，本地零落库。

## 二、数据源实测结论

以下均为连库实测值（非推断），是后续所有设计的依据。

| 项 | 实测值 | 影响 |
|----|--------|------|
| 视图行数 | 34173 | — |
| 员工数（`count(distinct "GH")`） | 34070 | 行 > 人，存在重复 |
| 重复工号 | 101 个工号命中 204 行 | 差异只落在身份证/合同主体等**未投影列**上；只投影业务列后 `distinct` 正好收敛为 34070 |
| 部门数（`distinct "组织编号"`） | 1384 | — |
| 部门重名 | 118 个部门名对应多个编号（"客户服务组" 21 个、"渠道业务组" 16 个） | **部门身份必须用 `组织编号`，不能按名称查** |
| 编号↔路径 | 同一个 `组织编号` 只对应一个 `组织全名称`（0 冲突） | 路径可作为稳定的层级前缀 |
| 全路径分隔符 | `_`（如 `杰克集团_杰克科技股份_营销军团`） | 部门名本身**不含** `_`，切分安全 |
| 路径层级分布 | L3~L7（L6 最多：528 个部门） | 树深度按路径段数即为层级 |
| 在职口径 | `ISWORK` 仅"在职/离职"两值；与 `STATE`（009/013/1/2/3/4/5/6/7/S10/010/011）多对一 | 过滤用 `ISWORK`，`STATE` 原样透出 |
| 一个工号的归属 | 不存在跨部门、跨在职状态的重复（`group by "GH" having count(distinct 组织编号)>1 or count(distinct ISWORK)>1` → 0 行） | 各部门人数之和 == 员工总数，树统计与分页 total 可对账 |
| 数据库版本 | Oracle 11.2.0.4 | **不支持 12c 的 `offset/fetch next`**，分页只能 `rownum`/`row_number()` |
| 视图查询成本 | 单扫 2.1~3.6 秒；全量拉取 5.8~6.0 秒 | 视图 = `distinct` + 8 个 LEFT JOIN，Oracle 侧成本，应用改不动 → 靠"少扫 + 缓存" |

## 三、技术方案

### 3.1 模块划分

```
StaffManagement/                聚合 pom（packaging=pom）
├── StaffManagement-api         Dubbo 契约：接口 + Query + DTO，纯 POJO，零框架依赖
└── StaffManagement-provider    可运行 Spring Boot 应用：web / service / dal
```

api 单独成模块是给消费方用的：**只含 lombok（optional）**，不传递任何 Spring/Dubbo 依赖，避免消费方被本应用的版本矩阵绑架。

### 3.2 版本矩阵（含两个必须记住的坑）

| 组件 | 版本 |
|------|------|
| Spring Boot | 4.1.1（Spring Framework 7.0.9） |
| Java | 21 |
| Apache Dubbo | 3.3.6（`dubbo-spring-boot-starter` + `dubbo-registry-nacos`） |
| Spring Cloud | 2025.1.3 |
| Spring Cloud Alibaba | 2025.1.0.0（nacos-discovery） |
| Oracle JDBC | ojdbc17 23.26.3.0.0（Boot 托管版本，已实测连通 11g） |
| 注册中心 | Nacos 169.254.180.49:8848（与 AtualCombatTraining 共用） |

`dependencyManagement` 的写法是**结论性的**，改动前务必读注释：

1. **不能 import `org.apache.dubbo:dubbo-bom`**。它会把自身编译期的 `spring-core` 钉到 5.3.39，盖掉 Boot 4.1.1 的 7.0.9，启动即 `NoSuchMethodError: SpringFactoriesLoader.forDefaultResourceLocation()`。改为只显式声明 `dubbo-spring-boot-starter`、`dubbo-registry-nacos` 两个入口坐标，其余 `dubbo-*` 由 starter 传递带入。
2. **`spring-cloud-dependencies` 必须排在 `spring-cloud-alibaba-dependencies` 之前**。只导 SCA 时它会连带把 `spring-cloud-commons/context` 定到 5.0.0，而 5.0.0 的 `CompositeCompatibilityVerifier` 只认 Boot 4.0.x，应用启动直接被拦（报错即"Spring Boot [4.1.1] is not compatible with this Spring Cloud release train"）。2025.1.3 带的是 5.0.3，与 Boot 4.1.1 匹配（gateway 模块同一套配法）。
3. 校验方式：不要只看 `dependency:tree`，以**产物 jar 为准**——`unzip -l target/*.jar | grep spring-cloud`。曾经出现过 tree 显示 5.0.3、jar 里仍是 5.0.0 的情况（未 clean 重打包）。

### 3.3 分层

```
web/StaffController          HTTP 薄封装：参数解析 + 统一响应 + 异常转 400/500
service/StaffQueryServiceImpl @DubboService，业务规则唯一落点（口径默认值、部门定位、层级还原）
service/DepartmentDirectoryService  部门目录缓存 + 子树还原
dal/StaffViewRepository      JdbcTemplate 直写 Oracle 11g 方言
dal/EmployeeRowMapper        结果集 → EmployeeDTO
```

Web 与 Dubbo 共用同一个 `StaffQueryServiceImpl`（Web 层直接注入本地 bean），保证两类调用方语义完全一致，不存在"HTTP 对了 Dubbo 错"的分裂。

异常映射：`IllegalArgumentException` → 400 + 中文原因（可直接展示）；`MethodArgumentTypeMismatchException`/`MissingServletRequestParameterException` → 400 + 参数格式提示。后者是 v1.1 补的——`@RestControllerAdvice` 里那条兜底的 `Exception` 处理器优先级高于 Spring 内置的 400 处理，不显式接住参数绑定异常就会把客户端的格式错误（如 `size=999999999999`）报成 500，既误导调用方也污染服务端错误率。其余异常一律 500 + 通用提示，堆栈只进日志。

刻意**不用 ORM**：视图 46 列、`distinct` + 8 个 LEFT JOIN、列名是中文必须加引号、11g 没有 offset/fetch——实体映射零收益，手写 SQL 反而最直白。

#### 为什么是 JdbcTemplate 而不是 MyBatis-Plus（含 SQL 注入审查结论）

同仓的 SpeechTraining / AtualCombatTraining 都用 `mybatis-plus-spring-boot4-starter`，本模块是唯一的例外，理由记录如下。

不用 MP 的实际原因只有一条硬的：**MP 的 `PaginationInnerInterceptor` 是 count 与数据两条 SQL**，接上 Oracle 方言后每次翻页都要两遍视图扫描（约 5 秒）；`count(*) over()` 的单扫写法用 `BaseMapper`/`Wrapper` 表达不出来，无论如何都得回落到手写 SQL。其余两条（46 列 distinct 投影、中文列名逐个 `@TableField("\"组织编号\"")`）只是让实体映射更没收益，不构成阻断。

**注入审查（2026-09-23，这是"是否可以不迁 MP"的判定依据）**：

- 静态：`StaffViewRepository` 内拼进 SQL 的片段**全部是编译期常量**（`VIEW`、`COLUMNS`、`SENSITIVE_COLUMNS`、固定的 where 片段）。四个可变入参——`keyword`、状态字面量、组织全路径前缀、分页窗口上下界——一律以 `?` 交给 `PreparedStatement` 绑定；`where` 这个 StringBuilder 只接受常量追加。全模块无任何 `String.format`/变量直拼。
- 类型面：`page`/`size` 在 Controller 就声明为 `int`，`status` 走 `WorkStatus.valueOf` 白名单枚举，`includeSensitive` 是 `boolean`。载荷型入参在到达 SQL 前已无字符串形态。
- 数据面：`deptCode`/`deptName` 不直接进 SQL——先在**内存里**过滤部门目录拿到唯一编号，命中后才用目录中的 `path` 作绑定参数，用户构造的编号根本查不到记录即 400。
- 通配符：`escapeLike` 先转义 `\`、`%`、`_` 再包 `%...%`，配合 `escape '\'`，避免 LIKE 通配符注入（等价于 MP 里要自己处理的 `${}` 场景）。
- 运行时实证（真机打载荷）：`' or 1=1 --`、`") or ("NAME" like "`、`%' union select "IDCARDNO" from dual--`、`%` 四种 keyword 载荷全部 `total=0`（注入成功应为 34070）；`deptCode=10201' or '1'='1`、`deptName=' or 1=1--`、`status=ACTIVE' or '1'='1` 全部 400 且不落库。

结论：**JdbcTemplate 写法在本模块不存在注入面**。需要说清的是，MP 在这方面并不更安全——`${}` 拼接一样能注入，防注入靠的是"只用 `#{}`/绑定变量"这一条纪律，与选哪个框架无关。所以这条不构成迁移理由。

真要统一技术栈，正确的迁法是**只换外壳不换 SQL**：建一个 Mapper XML、`resultType` 直接指到 api 模块的 `EmployeeDTO`、4 条 SQL 原样搬过去、不引入实体和 `BaseMapper`——这样和另两个模块对齐，同时保住单扫优化。属于一致性收益，不是安全性收益。

### 3.4 四条业务口径（已与需求方确认）

| 口径 | 取值 |
|------|------|
| 在职状态 | 默认只返回在职；`status` 可传 `ACTIVE`/`LEFT`/`ALL` 放开 |
| 敏感信息 | 手机号、身份证号、证件类型**默认不返回**（DTO 里为 null）；`includeSensitive=true` 才拼进投影 |
| 缓存 | 用 Redis（10.100.26.200:6379），不放进程内堆 |
| 模糊范围 | 姓名 + 英文名 + 工号三列 `like` |

### 3.5 分页 SQL

```sql
select * from (
  select e.*, row_number() over (order by GH) RN__, count(*) over () TOTAL__
  from ( select distinct <30 个业务列> from JACKSHR.V_BD_JACKMES_INFO where <条件> ) e
) where RN__ between ? and ?
```

- `count(*) over ()` 让"总数 + 本页数据"共用一次视图扫描。原方案 count 与数据各扫一遍是 5 秒级，改单扫后降到 2.1 秒级。
- 排序键用 `GH` 字符串而非 `to_number("GH")`：`GH` 是 NVARCHAR2 且有 `LH9415` 这类值，转数字直接 ORA-01722。
- 空页兜底：窗口函数算出的 `TOTAL__` 只在"本页至少有一行"时能读到。翻到范围外（如 `page=99&size=500`）会一行都没有，此时若不补查就会报 `total=0`，调用方误判成"整个查询没命中"。因此 `records` 为空且 `page>1` 时补一次 `select count(*) from (同样的内层 distinct 查询)`，实测该场景 `total` 回到真实值 10，正常页零额外开销。
- `size` 上限 500（`PagedQuery.MAX_SIZE`）；关键字必须非空，否则抛 400，防止模糊接口退化成全表拉取。
- LIKE 转义：用户输入里的 `%`、`_`、`\` 先转义再拼 `%...%`，配合 `escape '\'`，保证按字面量匹配（实测 `keyword=13%` 命中 0 条）。

### 3.6 部门层级树

**目录 + 明细两条路**：

1. **目录**（约 1384 行，含每个部门的在职/离职人数）来自一次全量聚合查询，缓存进 Redis，TTL 30 分钟。树的**结构**和**各级人数**全部由它在内存里还原，不查库。
2. **员工明细**仍按 `substr("组织全名称", 1, ?) = ?` 前缀过滤视图并分页。

目录聚合 SQL 的关键点（这里踩过一个静默错误）：内层必须 `group by 组织编号, ISWORK` 再 `count(distinct "GH")`。如果写成 `select distinct 组织编号, 组织名称, 组织全名称, ISWORK` 再按状态数行数，每个部门每个状态只剩 1 行，**人数会全部退化成 0/1**——树看起来结构正常、数字却全错（实测该 bug 下 `营销军团` 报 164 人，真实 939 人）。

子树还原规则：

- 目录里只有"挂了员工"的部门，中间层可能缺号。按 `组织全名称` 切分 `_` **补齐缺失的中间节点**，保证结构与真实组织一致，而不是把断档的下级直接挂到上层。
- 递归建节点时"先入表再挂父"，避免断档路径向上递归时死循环。
- `totalEmployeeCount` 后序遍历回填 = 本级直属 + 全部下级；`directEmployeeCount` 只算挂名在本级的员工。
- 校验通过：`营销军团` 在职 939、`status=ALL` 1874，与视图原始扫描计数完全一致；`东南亚战区` 7 个部门 30 人，树 total 与分页 total 相等。

部门定位规则：

- `deptCode` 优先。编号不存在 → 400。
- 只给 `deptName` 时，命中 1 个才放行；**重名不猜**，直接 400 并把全部候选（`编号=全路径`）抛回调用方。
- 两个都不给 → 400。

### 3.7 Redis 缓存

| 项 | 值 |
|----|----|
| key | `staff:dept:directory:v2`（v1 是"人数恒为 0/1"的错误口径，换 key 让脏数据自然过期） |
| 结构 | 单个 String，每部门一行，字段用 `\t` 分隔：`编号 \t 名称 \t 全路径 \t 在职数 \t 离职数` |
| TTL | 30 分钟；未命中回源 Oracle 并写回 |
| 为什么不用 JSON | Boot 4 同时存在 Jackson 2/3，手写序列化反而要绑一个具体版本；目录是定长扁平结构，制表符分隔即可 |
| 降级 | 读写 Redis 的异常都 catch 住打 WARN 并回源，缓存不可用不影响功能 |

`size=0` 表示"只要结构和人数、不要明细"，此时**一次库都不回**，纯缓存返回（实测 89 毫秒）。

### 3.8 Dubbo 暴露

```java
@DubboService(version = "1.0.0", timeout = 30_000)
public class StaffQueryServiceImpl implements StaffQueryService { ... }
```

| 配置 | 值 | 原因 |
|------|----|------|
| `dubbo.protocol.port` | 20881 | 20880 被本机其他 Dubbo 进程占用 |
| `dubbo.application.qos-port` | 22223 | 同上，22222 冲突 |
| `dubbo.application.register-mode` | **interface** | 应用级注册会用服务名 `StaffManagement` 往 Nacos 再写一个**端口 20881** 的实例；网关按服务名做负载均衡时会把 HTTP 流量打到 Dubbo 端口 |
| 序列化 | hessian2（prefer 附带 fastjson2） | 默认即可，已实测跨进程往返 |
| 序列化白名单 | `StaffManagement-api/src/main/resources/security/serialize.allowlist` 内写 `jack.digityhuman.staffmanagement.api` | 资源随契约 jar 发布，消费方引依赖即自动生效 |

`timeout=30_000` 是给"视图 2~3 秒 + 冷缓存"留的量，不是随手写的大数。

### 3.9 已验证结论（真机）

- 启动：Tomcat 8083、Dubbo 20881、Nacos 注册成功（`DEFAULT_GROUP StaffManagement 169.254.180.49:8083`、`Register: dubbo://192.168.81.1:20881/...StaffQueryService...version=1.0.0`）。
- 独立消费方进程经 Nacos 发现并调用成功：代理获取 3670 毫秒，`searchEmployees`/`listDepartmentStaff` 返回值与 HTTP 接口一致，树结构完整，`IllegalArgumentException` 能跨进程抛回（重名 21 个候选）。
- 敏感字段：默认 null，`includeSensitive=true` 时返回真实手机号/身份证。
- 时延：热态模糊查询 0.37 秒；冷态 2.1~3.6 秒；部门接口冷 6.4 秒（含目录回源）、暖 2.9 秒、`size=0` 0.089 秒。

## 四、遗留与后续

| 项 | 说明 |
|----|------|
| 视图成本 | 2~3 秒是视图自身的 `distinct`+8 个 LEFT JOIN 造成的，需 DBA 侧优化才能根治；当前用"单扫 + 目录缓存"绕过 |
| 组织变动延迟 | 部门目录最长 30 分钟不一致；组织调整频繁的时段可缩短 TTL 或提供手动清缓存入口 |
| 后续 Dubbo 方法 | 契约已按"一个查询一个方法 + 一个 Query 对象"排布，新增方法只加接口方法和 Query 子类，不改现有签名 |
| 权限 | 若要做"只能查自己部门"的越权控制，落点在 `StaffQueryServiceImpl`（Web 与 Dubbo 同一条路径） |
