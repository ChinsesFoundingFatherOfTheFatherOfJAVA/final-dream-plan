# 员工信息管理模块 - 后端接口文档

> 版本：v1.1（2026-09-23）　Web 端口：`8083`　Dubbo 端口：`20881`
> 变更记录：v1.1 补「参数格式错误统一回 400」（原先 `size` 超出 int 范围等客户端错误会误报 500）、`includeSensitive` 的宽松布尔转换说明；v1.0（2026-09-21）首版
> 应用名：`StaffManagement`
> 数据源：Oracle `JACKSHR.V_BD_JACKMES_INFO`（只读视图，34070 名员工 / 1384 个部门）
> 本文所有示例均为真机返回值的真实截取（仅样例数量有删减，字段值未改写）

## 〇、通用约定

### 响应包装

```json
{ "code": 0, "message": "ok", "data": { } }
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 0=成功；非 0 见下表 |
| message | string | 成功固定 `ok`；失败为**可直接展示给用户的中文原因** |
| data | object\|null | 业务数据，失败时为 null |

### 错误码

| code | HTTP | 场景 | message 示例 |
|------|------|------|-------------|
| 400 | 400 | 参数格式错误：`size` 超 int 范围、必填 `keyword` 缺失、查询串含无法按 UTF-8 解码的字节 | `请求参数格式不正确：keyword 必填，page/size 需为整数且 size 不超过 500，status 只支持 ACTIVE/LEFT/ALL` |
| 400 | 400 | 参数不合法（口径可判定） | `keyword 不能为空：模糊查询必须给关键字，避免全表拉取 34173 行` |
| 400 | 400 | 组织编号不存在 | `组织编号不存在: 999999999` |
| 400 | 400 | 组织名称重名（不猜，返回候选） | `组织名称 "客户服务组" 有 21 个重名部门，请改用组织编号查询。候选: 102013302=杰克集团_...; ...` |
| 400 | 400 | status 取值非法 | `status 只支持 ACTIVE / LEFT / ALL，收到: xxx` |
| 500 | 500 | 未预期异常 | `员工查询服务暂时不可用，请稍后重试`（堆栈只进服务端日志，不外泄） |

Dubbo 侧同样抛 `IllegalArgumentException`，可跨进程传回（已实测）。

### 公共参数

| 参数 | 类型 | 默认 | 说明 |
|------|------|------|------|
| status | string | `ACTIVE` | `ACTIVE`=仅在职、`LEFT`=仅离职、`ALL`=全部；忽略大小写 |
| page | int | 1 | 从 1 开始 |
| size | int | 20 | **上限 500**（超出自动收敛为 500）；部门接口可用 `0` 表示"只要结构与人数，不取明细" |
| includeSensitive | boolean | false | true 时才返回手机号/身份证号/证件类型。注意 Spring 的布尔转换是宽松的，`yes`/`on`/`1` 等同 true |

### 时延预期（实测）

| 场景 | 冷 | 热 |
|------|----|----|
| 模糊查询 | 2.1~3.6 s | 0.37 s |
| 部门接口（含明细） | 6.4 s（目录回源） | 2.9 s |
| 部门接口 `size=0` | — | **0.089 s（纯缓存）** |

视图本身是 `distinct` + 8 个 LEFT JOIN，单次扫描 2~3 秒为 Oracle 侧固定成本。前端/调用方**必须按秒级设计超时与 loading**，Dubbo 消费方超时建议 ≥ 30 秒。

## 一、员工模糊查询

**GET** `/api/staff/employees`

关键字同时对 **中文姓名、英文姓名、工号** 三列做包含匹配；关键字里的 `%`、`_`、`\` 按字面量处理（不会被当成通配符）。

**请求参数**: `keyword`（必填）+ 公共参数

```
GET /api/staff/employees?keyword=张伟&page=1&size=3
```

**响应**（真实值）:
```json
{
 "code": 0, "message": "ok",
 "data": { "page": 1, "size": 3, "total": 10, "records": [ /* EmployeeDTO[] */ ] }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| total | long | 命中总人数（与本页共用一次扫描得到）。翻到范围外时 `records` 为空但 `total` 仍是真实总数 |
| records | EmployeeDTO[] | 按工号字典序升序 |

**业务校验**:

| 场景 | 结果 |
|------|------|
| `keyword` 缺失/空白 | 400，见错误码表 |
| `size` > 500 | 收敛为 500，不报错 |
| `page` 超出范围 | 200 + 空 `records` + 真实 `total` |

同一关键字在不同口径下的命中数（实测 `keyword=张伟`）：`ACTIVE`=10、`LEFT`=14、`ALL`=24。

## 二、部门员工查询（含下级层级）

**GET** `/api/staff/departments/employees`

查指定部门**及其全部下级部门**的员工，同时把该部门下的层级结构还原成树返回。

**请求参数**: `deptCode` 或 `deptName`（至少一个，编号优先）+ 公共参数

```
GET /api/staff/departments/employees?deptCode=10201&size=0     # 只看组织骨架与人数
GET /api/staff/departments/employees?deptCode=1020139&size=20  # 骨架 + 第一页明细
```

**响应**（`deptCode=1020139`、`size=1` 的真实返回，`tree.children` 只保留前 2 个）:
```json
{
 "code": 0, "message": "ok",
 "data": {
  "deptCode": "1020139",
  "deptName": "东南亚战区",
  "deptPath": "杰克集团_杰克科技股份_营销军团_东南亚战区",
  "level": 4,
  "departmentCount": 7,
  "totalEmployeeCount": 30,
  "tree": {
   "deptCode": "1020139", "deptName": "东南亚战区",
   "deptPath": "杰克集团_杰克科技股份_营销军团_东南亚战区",
   "level": 4, "directEmployeeCount": 1, "totalEmployeeCount": 30,
   "childCount": 6,
   "children": [
    { "deptCode": "10201140501", "deptName": "印尼办事处",
      "deptPath": "杰克集团_杰克科技股份_营销军团_东南亚战区_印尼办事处",
      "level": 5, "directEmployeeCount": 5, "totalEmployeeCount": 5, "childCount": 0, "children": [] },
    { "deptCode": "102013801", "deptName": "大客户业务组",
      "deptPath": "杰克集团_杰克科技股份_营销军团_东南亚战区_大客户业务组",
      "level": 5, "directEmployeeCount": 8, "totalEmployeeCount": 8, "childCount": 0, "children": [] }
   ]
  },
  "employees": { "page": 1, "size": 1, "total": 30, "records": [ /* EmployeeDTO[] */ ] }
 }
}
```

**DepartmentStaffDTO**:

| 字段 | 类型 | 说明 |
|------|------|------|
| deptCode / deptName / deptPath | string | 入参定位到的部门本身 |
| level | int | 该部门层级 = `deptPath` 按 `_` 切分的段数（1=集团） |
| departmentCount | int | 子树内部门总数（**含自身**） |
| totalEmployeeCount | int | 子树内员工总数，等于 `tree.totalEmployeeCount`，与 `employees.total` 一致 |
| tree | DepartmentNodeDTO | 层级树，根即本部门 |
| employees | PageResult | 子树内员工**明细，扁平分页** |

**DepartmentNodeDTO**（递归）:

| 字段 | 类型 | 说明 |
|------|------|------|
| deptCode | string\|null | 补出来的中间节点没有编号（该层级无员工挂名） |
| deptName | string | 取自 `deptPath` 最后一段 |
| deptPath | string | 全路径，同时是排序键 |
| level | int | 层级 |
| directEmployeeCount | int | **直属**：挂名在本部门（不含下级）的员工数 |
| totalEmployeeCount | int | **累计**：本级 + 全部下级 |
| childCount | int | 直接下级个数（等于 `children.length`，便于懒渲染） |
| children | DepartmentNodeDTO[] | 下级，按 `deptPath` 升序 |

**为什么明细是扁平的**：分页窗口会跨多个部门，把明细按部门分组后再分页会出现"某一页里某个部门只有一半人"的假分组。因此**明细平铺 + 每行自带 `deptCode`/`deptPath`**，树只负责表达层级与人数；前端要做"按部门展开"时用行的 `deptCode` 关联到 `tree` 节点即可。

**业务校验**:

| 场景 | 结果 |
|------|------|
| 只给 `deptName` 且重名 | 400 + 全部候选 `编号=全路径` |
| `deptCode` 不存在 | 400 |
| 两个都不给 | 400 `deptCode 与 deptName 至少给一个` |
| `size=0` | 只回结构与人数，完全不查库（纯 Redis） |

**实测参考值**：`10201 营销军团` → 225 个部门、在职 939 人、`status=ALL` 1874 人、根有 31 个直接下级；叶子部门 `102013802 渠道业务组` → 1 个部门、2 人、无下级。

## 三、员工字段字典（EmployeeDTO）

默认投影 31 个业务字段 + 3 个敏感字段（`includeSensitive=false` 时敏感字段为 null）。

| 字段 | 类型 | 视图列 | 含义 / 实测取值 |
|------|------|--------|---------------|
| gh | string | `GH` | 工号，NVARCHAR2，含 `LH9415` 这类字母前缀，**不能转数字** |
| name | string | `NAME` | 中文姓名 |
| enName | string | `ENNAME` | 英文姓名（部分记录回填的是拼音/中文） |
| sex | string | `SEX` | 男 / 女 / `-` |
| birthday | date | `BIRTHDAY` | `yyyy-MM-dd` |
| hireDate | datetime | `HIREDATE` | 入职日期 |
| workAge | decimal | `WORKAGE` | 工龄（年，带小数，如 `0.58`、`9.01`） |
| age | int | `AGE` | 年龄 |
| company | string | `COMPANY` | 合同主体公司名称 |
| companyId | string | `COMPANYID` | 公司编号（如 `1000`=杰克科技股份有限公司） |
| empTypeCode / empTypeName | string | `EMPTYPECODE`/`EMPTYPENAME` | 员工类型，如 `10`=生产、`20`=科室 |
| posiCode / posiName | string | `POSICODE`/`POSINAME` | 岗位，如 `004075` / 渠道销售经理 |
| deptCode | string | `"组织编号"` | **部门唯一标识**（名称有 118 个重名，不可当键） |
| deptName | string | `"组织名称"` | 本部门名称 |
| deptPath | string | `"组织全名称"` | 全路径，`_` 分隔 |
| deptLevel | int | 由 `deptPath` 算出 | 层级 = 段数 |
| stateCode | string | `STATE` | 人事状态原码：009/013/011/010/1/2/3/4/5/6/7/S10 |
| workStatus | string | `ISWORK` | 在职 / 离职（`STATE` 与之多对一） |
| empGroup | string | `EMPGROUP` | 员工组：正式员工、返聘 等 |
| jobGrade | string | `JOBGRADE` | 职级，如 `P2-2`、`O4` |
| workplace | string | `WORKPLACE` | 工作地点编码 |
| highestDegree | string | `HIGHESTDEGREE` | 最高学历，如 `大专（高职）`、`初中` |
| nativePlace | string | `JIGUAN` | 籍贯 |
| directCode / directName | string | `DIRECT`/`DIRECTNAME` | 直属上级工号/姓名，可能为 null |
| sapNumber | string | `SAPNUMBER` | SAP 工号（`50011375`），离职/外部人员常为 null |
| nationality | string | `NATIONALITY` | 国籍，如 `CN` |
| effectiveTime | datetime | `EFFECTIVETIME` | 当前人事记录生效时间 |
| lastChange | datetime | `LASTCHANGE` | 最后变更时间（视图侧刷新时刻，精度到毫秒） |
| **mobile** | string | `FNCELL` | 手机号 —— **敏感，默认 null** |
| **idCardNo** | string | `IDCARDNO` | 身份证号 —— **敏感，默认 null** |
| **idType** | int | `IDTYPE` | 证件类型，实测取值见到 `1`（与 18 位身份证号同现）；**码值含义未在视图内注明，如需精确口径请找 SHR 侧确认** |

## 四、Dubbo 服务契约

### 4.1 引入依赖

```xml
<dependency>
    <groupId>jack.digityHuman</groupId>
    <artifactId>StaffManagement-api</artifactId>
    <version>0.0.1-SNAPSHOT</version>
</dependency>
```

契约包只含接口 + POJO（lombok 为 optional），不传递 Spring/Dubbo 版本。序列化白名单资源 `security/serialize.allowlist` 已打进这个 jar，消费方无需额外配置。

### 4.2 接口

```java
package jack.digityhuman.staffmanagement.api;

public interface StaffQueryService {
    PageResult<EmployeeDTO> searchEmployees(EmployeeSearchQuery query);
    DepartmentStaffDTO listDepartmentStaff(DepartmentStaffQuery query);
}
```

| 项 | 值 |
|----|----|
| interface | `jack.digityhuman.staffmanagement.api.StaffQueryService` |
| version | `1.0.0` |
| group | 无（空） |
| 注册中心 | `nacos://169.254.180.49:8848`，**接口级注册**（`register-mode=interface`） |
| 协议 / 端口 | `dubbo` / 20881 |
| provider 侧超时 | 30000 ms |
| 序列化 | hessian2 |

### 4.3 消费方声明

```java
@DubboReference(version = "1.0.0", timeout = 30_000)
private StaffQueryService staffQueryService;
```

或纯 API 方式（无需 Spring，本项目验证用的就是这种）：

```java
ReferenceConfig<StaffQueryService> ref = new ReferenceConfig<>();
ref.setApplication(new ApplicationConfig("your-app"));
ref.setRegistry(new RegistryConfig("nacos://169.254.180.49:8848"));
ref.setInterface(StaffQueryService.class);
ref.setVersion("1.0.0");
StaffQueryService svc = ref.get();
```

### 4.4 入参对象

`EmployeeSearchQuery` / `DepartmentStaffQuery` 都继承 `PagedQuery`：

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| status | WorkStatus | ACTIVE | 枚举 `ACTIVE`/`LEFT`/`ALL`；服务端 `normalize()` 会把 null 收敛为 ACTIVE |
| page | int | 1 | ≥1 |
| size | int | 20 | 0~500，超出即钳制 |
| includeSensitive | boolean | false | 敏感字段开关 |
| keyword | string | — | 仅 `EmployeeSearchQuery`，必填 |
| deptCode / deptName | string | — | 仅 `DepartmentStaffQuery`，至少一个 |

**语义与 HTTP 完全一致**（同一实现类），包括：空关键字抛 `IllegalArgumentException`、部门重名抛 `IllegalArgumentException` 并在 message 里列候选编号、`size=0` 只回结构不查库。
