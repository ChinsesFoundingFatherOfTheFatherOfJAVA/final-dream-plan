# P1 Native Runtime 实施偏差与最终决策

> 日期：2026-10-22
> 范围：自由演练助手 P1；P2/P3 不包含在本轮实现内。
> 结论：以下为当前代码的最终口径；与 01~03 规划文档冲突时，以本文件为准。

## 1. 模型与供应商

| 项 | 原规划 | 最终方案 | 原因 |
|---|---|---|---|
| 模型来源 | 本地 vllm / Qwen3-30B | 千问 AI 平台 OpenAI-compatible 接口 | 当前环境没有本地模型；实测 `qwen3.8-flash` 的 tool calling、JSON、长上下文可用 |
| API 地址 | vllm 内网地址 | `https://maas.qianwenaiapi.com/compatible-mode/v1` | 与现有 TTS/DashScope 凭据链路一致 |
| 凭据 | 新增长期 key | 复用 `SPEECH_DASHSCOPE_API_KEY` | 不把真实 key 写入仓库；key 由进程环境注入 |

`glm-4.7-flash` 实测多次 429，已放弃；千问 `qwen3.8-flash` 为当前选定模型。

## 2. 工具调用

- 工具执行仍由 AtualCombatTraining 负责，AIGentService 只通过 HTTP 调用
  `/api/act/internal/tools/{create_topic|update_artifact|generate_theme|generate_cases}`。
- 原 01/02 规划中的 Dubbo 工具化未在 P1 实施；HTTP 直连已满足最小闭环，且保留工具业务单一实现。
- 工具 JSON Schema 的数组元素已按真实请求 DTO 修正：
  - `audiences`：`string[]`
  - `scenarioIds`：`string[]`
  - `patches`：`object[]`
- native 失败不会在同一轮自动切 Dify：工具可能已经产生业务副作用，自动重试会重复执行。
  运维切回 `agent.chat.provider=dify` 后从下一轮重试。

## 3. 记忆与流式

- P1 只实现 L1 `SessionMemory`：进程内按 `sessionId` 保存最近 24 条消息，并记录是否已交付
  结构化场景规划。
- 不实现 Redis L2 / DB L3；服务重启、多实例部署不共享会话。
- `InternalAgentController` 当前等待模型完整返回后发送一个 `agent_message`，再发 `message_end`；
  不是逐 token SSE。前端协议兼容，但体验会和 Dify 的逐字流不同。

## 4. 运行时与配置

- AIGentService 端口：`8086`。
- `agent.react.max-iterations=80`，已从硬编码 8 改为配置。
- AIGentService 作为 agent runtime 不依赖 MySQL/Nacos discovery；已移除骨架里的
  `after-end-common` 与 Nacos discovery 依赖，避免空服务启动时误触发 DataSource。
- AtualCombatTraining 新增：
  - `agent.chat.provider=${ACT_AGENT_CHAT_PROVIDER:dify}`
  - `agent.chat.native.base-url=${ACT_AGENT_NATIVE_BASE_URL:http://localhost:8086}`
  - `agent.chat.native.timeout-ms=300000`
- provider 当前按进程启动配置生效；未接 Nacos 动态刷新，切换 native/dify 需要重启
  AtualCombatTraining。达到“不重启切换”仍需要后续 Nacos config 接入。
- native 调用复用 `act_ai_call_log`（appKind=`orchestrator`）记录成功/失败/耗时；
  不新增数据库表，避免 P1 引入额外迁移。
- `agent.chat.native.*` 由独立 `NativeAgentProperties` 绑定，避免 `nativeRuntime`
  字段 relaxed binding 误落到 `native-runtime.*`。

## 5. 阶段守卫

- 新会话只有出现具体方向（行业/对象/目标等）才允许 `create_topic`；
  “我想做培训，你看着办”这类模糊输入只允许追问。
- 判断 `create_topic` 方向时可合并前几轮用户文本，支持“按刚才的信息创建”；
  但生成类工具的“明确确认”只认当前轮，不接受历史里的“可以”。
- `generate_theme` 需要已有主题、用户明确确认、且会话中已交付结构化场景规划。
- `generate_cases` 需要已有主题、用户明确确认、且产物摘要中场景数至少为 1。
- 守卫是业务安全边界，prompt 约束不是唯一防线。
