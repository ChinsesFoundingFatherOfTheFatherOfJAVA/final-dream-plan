## 0. 通用约定

### 0.1 调用拓扑（谁调谁）

```
前端 ──WS──> AtualCombatTraining（WS栈/落库/事件推送 全留守，零改动）
                │ AssistantChatService 按 provider 开关分流
                ├──(dify)──> Dify 10.10.166.13（灰度期保留）
                └──(native)─HTTP──> AIGentService /internal/agent/chat（SSE）
                                          │ ReAct 引擎执行中
                                          └──HTTP──> AtualCombatTraining InternalToolController
                                                        （工具执行后本地直推 bizType WS 事件）

SpeechTraining ──HTTP──> AIGentService /internal/agent/task/*（阻塞/流式）
AtualCombatTraining(主题/案例生成) ──HTTP──> AIGentService /internal/agent/task/*
AIGentService(DbRebuilder 降级重建) ──Dubbo──> AtualCombatTraining AgentMemoryQueryService
```

- **全部接口为服务间直连**（内网），不经网关；网关路由 `/api/agent/**` 仅作预留。
- 地址配置：消费方 properties 增加 `aigent.base-url=http://<host>:<port>`（对齐现有 `dify.base-url` 配置模式）。
- 认证：内网边界（对齐 InternalToolController 的纵深防御口径）；可选 `X-Internal-Token` 简单共享密钥（P0 决定，默认不启用）。
- 链路追踪：所有请求携带 `traceId` 字段（对齐现有 Dify 调用审计字段），AIGentService 日志与 DifyCallLog 记录贯穿。

### 0.2 响应包（阻塞接口）

```json
{ "code": 0, "message": "success", "data": { } }
```

对齐工程既有 `ApiResponse`；非 0 为业务失败，`message` 直接可读（会出现在工具观察结果或上层异常里）。

### 0.3 超时基线（对齐现网 dify.* 配置）

| 调用 | 超时 |
|------|------|
| 会话流式 /internal/agent/chat | 300s（= dify.agent-timeout-ms），首 token 30s |
| theme-gen 流式 | 600s（= dify.theme-timeout-ms） |
| case-gen / 其他任务 | 120s（= dify.case-timeout-ms） |
| Dubbo 工具：generate_theme | 120s（异步受理型实际秒回，兜底） |
| Dubbo 工具：其余 3 个 | 10s |

## 1. INT-1 内部会话流式接口（AG-04 自由演练助手）

### INT-1.1 `POST /internal/agent/chat`

**职责**：执行自由演练助手一轮对话（ReAct 循环 + 三层记忆），以 SSE 流式返回。**SSE 事件格式克隆 Dify `/v1/chat-messages` streaming 协议**，消费端 NativeAgentClient 平移 DifyAgentClient 代码结构（onChunk/onConversationId 回调同构），改动量最小化。

**请求体**：

```json
{
  "sessionId": "f81d4fae-7c56-45c6-a7c4-a00c12e90ab",
  "traceId": "tr-20261010-0001",
  "query": "帮我规划一个客户投诉处理的演练主题",
  "inputs": {
    "theme_status": "主题《客户投诉处理》已创建，规划中",
    "artifact_summary": "已生成场景2个；画像1份；冰山模型未生成",
    "material_summary": "用户上传了《客服手册》摘要3000字"
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| sessionId | string | 是 | 本地会话 ID；AIGentService 以此键管理三层记忆（= Dify 的 conversation_id 角色） |
| traceId | string | 是 | 本轮追踪 ID（工具 bizType 事件关联用） |
| query | string | 否 | 用户输入。**空/缺省 = 首轮开场或恢复会话**——引擎按 SessionMemory 判断（见 INT-1.3），**不再有伪 query** |
| inputs | object | 否 | 上下文三变量，字段名与现网 Dify 调用一致（theme_status/artifact_summary/material_summary） |

**响应**：`Content-Type: text/event-stream`，SSE 帧 `data: {JSON}`，事件集与 DifyAgentClient 消费的三种事件**完全同构**：

| 事件 | data 字段 | 语义 | 消费端动作（NativeAgentClient，平移 DifyAgentClient） |
|------|-----------|------|------|
| `agent_message` | `answer`（文本增量）、`conversation_id` | 助手回答增量（含工具调用轮之间的过渡文本） | `onChunk(answer)` → RoundWriter.writeText（WS part-content, text_delta） |
| `message_end` | `task_id`、`message_id`、`conversation_id` | 本轮收尾 | taskHolder/messageIdHolder 回填（现有收尾逻辑不变） |
| `error` | `message` | 失败（看门狗超时/LLM 连败/引擎异常） | 结果带 errorMessage → 上层翻成 session-finish 带 error |
| `ping` | `ts` | 心跳 | 忽略（现有口径） |

> `conversation_id` 一律回传 `sessionId`（兼容消费端回存逻辑；native 模式无独立会话 ID 概念）。`task_id`/`message_id` 由 AIGentService 生成 UUID。

**帧序列示例**（一轮含 1 次工具调用的回复）：

```
data: {"event": "agent_message", "conversation_id": "f81d...", "answer": "好的，"}
data: {"event": "agent_message", "conversation_id": "f81d...", "answer": "我先帮您建立主题。"}
data: {"event": "agent_message", "conversation_id": "f81d...", "answer": "主题已创建。接下来我们规划场景……"}
data: {"event": "message_end", "task_id": "task-uuid-1", "message_id": "msg-uuid-1", "conversation_id": "f81d..."}
```

> 工具调用（create_topic 等）在引擎内部经 Dubbo 执行，**其 bizType 事件（topic-changed 等）由 AtualCombatTraining 工具执行侧直推 WS**（与现 InternalToolController 行为一致），**不在本 SSE 上回传**——这是"前端零改动"的关键：正文 text part 与 bizType data part 的交织仍由本地 RoundWriter 完成。

**引擎侧约定**：
- ReAct 迭代上限 80（对齐 DSL）；vllm function calling（tools 参数），不可用时降级文本 JSON 协议（02 §7）。
- 工具连续失败 2 次停止重试该工具；LLM 输出校验 3 连败 → `error` 事件收尾。
- 每轮结束 SessionMemory 持久化（L1 更新 + L2 异步写）。

### INT-1.2 前端不变契约（对照基准，不新增开发）

前端连接与帧协议**完全不变**，code agent 无需触碰前端：

- WS 端点：`/api/act/ws/chat?sessionId={id}`（WsChatHandler，心跳 ping 20s / pong 80s）
- 单轮帧序列：`user-message-ack → session-start → message-extra-info → message-start → N×[part-start → part-content×M → part-end] → session-finish`，seq 单轮递增、part index 从 0 递增（WsFrameEncoder 现有规则）
- 工具 bizType 事件：`biz-side-manage-topic-changed` / `artifact-updated` / `artifact-generated` / `case-generated`（data part，part-end 整体解析）

### INT-1.3 会话语义（伪 query 根治 + 双轨期注意）

| 场景 | 现网（Dify 路径） | native 路径 |
|------|------|------|
| 新会话首轮 | AssistantChatService 伪造 `SESSION_START_QUERY_NEW` 作为 query | query 传空；引擎检测 SessionMemory 无消息 → is_first_turn=true → instruction 首轮规则开场 |
| 恢复会话 | 伪造 `SESSION_START_QUERY_RESUMED` | query 传空；引擎从 L2/L3 装载历史 → 注入 system 消息"简要说明当前进展" |
| 正常轮 | 真实 query + conversation_id | 真实 query（SessionMemory 自动带上下文） |

> **双轨期约束**：`SESSION_START_QUERY_NEW/RESUMED` 常量在 Dify 分支仍被使用（fallback 需要），**灰度期只改 native 分支不发送伪 query**；全量切流（P3 后）才删除常量与 Dify 分支代码。

## 3. INT-3 流式任务接口 `POST /internal/agent/task/theme-gen/stream`（AG-05 主题生成）

**为什么单独流式**：主题生成依赖 Dify workflow streaming 的**节点完成事件**驱动右面板"渐次出现"（场景 → 画像+冰山 → 维度），现网 ThemeGenerationServiceImpl 用 `DifyWorkflowEventParser.Listener(nodeId, title, outputs)` 消费。本接口克隆该事件协议。

**请求体**（inputs 与现网 buildInputs 逐字段一致）：

```json
{
  "sessionId": "…", "traceId": "…",
  "inputs": {
    "goal": "提升客服投诉处理能力",
    "audiences": "[\"一线客服\"]",
    "material_summary": "《客服手册》摘要…（重试时拼接校验错误）",
    "keep_existing": "false",
    "existing_scenes": "[\"退换货纠纷\",\"服务态度投诉\"]"
  }
}
```

**响应**：SSE，事件克隆 Dify workflow streaming：

| 事件 | data 字段 | 语义 |
|------|-----------|------|
| `node_finished` | `node_id`、`title`、`outputs` | 一个步骤完成 |
| `message_end` / `error` | 同 INT-1 | 收尾/失败 |

**node_finished 的 node_id/title/outputs 平移 DSL 原值**（消费端 buildPartialFromNode 按 outputs 变量名识别，必须逐字段对齐）：

| step | node_id（DSL 原值） | title | outputs 变量 |
|------|------|------|------|
| 解析场景 | `code_scenes` | 解析场景JSON | `scenes_json` |
| 解析画像冰山 | `code_profiles` | 解析画像冰山JSON | `profiles_json`、`iceberg_json` |
| 聚合输出 | `code_merge` | 聚合校验输出 | `scenes_json`/`profiles_json`/`iceberg_json`/`criteria_json`/`materials_json` |

最终 outputs（message_end 前或独立 `workflow_finished` 事件）：`artifact_json`（string，聚合产物 JSON 串——消费端 parseArtifact 逻辑不动）。

**消费端改动**：ThemeGenerationServiceImpl 把 `workflowClient.runStreaming(...)` 换成按开关分流（native → NativeWorkflowClient 调本接口；dify → 原路径），重试（MAX_ATTEMPTS + 错误拼入 material_summary）、ArtifactSchemaValidator 校验、mergeGeneratedPartial、事件推送**全部不动**。

## 4. DUB-1 Dubbo 工具契约（AtualCombatTraining 暴露，AIGentService 消费）

### 4.1 接口定义

InternalToolController 四端点逻辑下沉为 `AgentToolService`（`@DubboService`，Controller 过渡期保留给 Dify 分支）：

```java
public interface AgentToolService {
    /** 2.5.1 建立草稿主题 + 推 topic-changed */
    CreateTopicResp createTopic(String sessionId, String traceId, CreateTopicReq req);
    /** 2.5.3 受理主题生成（异步）+ 推 artifact-generated */
    AcceptedResp generateTheme(String sessionId, String traceId, GenerateThemeReq req);
    /** 2.5.4 受理案例生成（异步逐场景）+ 推 case-generated */
    AcceptedResp generateCases(String sessionId, String traceId, GenerateCasesReq req);
    /** 2.5.2 JSON-Patch 更新工作区 + 推 artifact-updated */
    UpdateArtifactResp updateArtifact(String sessionId, String traceId, ArtifactPatchesReq req);
}
```

> sessionId/traceId 原为 HTTP query 参数，Dubbo 化后入参传递（工具执行侧据此取当前轮 RoundWriter 推 bizType 事件——**与现 InternalToolController 完全同机制**）。

### 4.2 DTO（字段与现网 DTO 一致，直接复用类）

| DTO | 字段 |
|-----|------|
| CreateTopicReq | topic, description |
| GenerateThemeReq | goal, audiences(List\<String\>), materialSummary, keepExisting(Boolean) |
| GenerateCasesReq | scenarioIds(List\<String\>), difficulty(Integer) |
| ArtifactPatchesReq | patches(Object) |
| CreateTopicResp | themeId, created |
| AcceptedResp | accepted, hint |
| UpdateArtifactResp | versionNo |

### 4.3 语义与纪律

- **响应会被引擎当作工具观察结果喂回模型**——只回必要字段（现网口径，DTO 已最小化）。
- 工具描述（何时调用/禁止调用）从 DSL extra.description 原样平移为 ToolRegistry 注册元数据。
- generate_theme/generate_cases 是**受理即返回**型（异步生成 + 事件推送），引擎拿到 accepted 后继续对话，不等生成完成。
- 工具执行的业务逻辑（落库/版本/事件推送）零改动，仅入口从 HTTP 换 Dubbo。

## 7. Redis 数据结构（AG-03）

Key 一律 `agent:` 前缀（与 StaffManagement 部门缓存隔离）：

| Key | 类型 | TTL | 说明 |
|-----|------|-----|------|
| `agent:session:{sessionId}` | String(JSON) | 7 天（每次写续期） | L2 会话态 |
| `agent:lock:{sessionId}` | String | 30s | 会话写锁（防并发写） |

`agent:session:{sessionId}` 值示例：

```json
{
  "messages": [
    { "role": "system", "content": "instruction全文或恢复会话提示", "meta": { "isFirstTurn": true } },
    { "role": "user", "content": "帮我规划一个投诉处理主题" },
    { "role": "assistant", "content": "好的…", "toolCalls": [ { "name": "create_topic", "args": { "topic": "客户投诉处理" } } ] },
    { "role": "tool", "content": "{\"themeId\":\"t-123\",\"created\":true}" }
  ],
  "inputs": {
    "themeStatus": "主题《客户投诉处理》已创建，规划中",
    "artifactSummary": "已生成场景2个",
    "materialSummary": "《客服手册》摘要3000字"
  },
  "updatedAt": "2026-10-10T14:30:00",
  "version": 12
}
```

- `version` 乐观锁：写 L2 时比对递增；冲突放弃本次写并告警（L3 是事实源，最坏回退重建）。
- 工具执行成功 → inputs 缓存失效（artifact_summary 等下轮重算，02 §4.2）。
