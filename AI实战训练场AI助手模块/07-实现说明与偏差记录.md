## 3. 偏差记录（实现与 02/03 文档不一致处）

### D1 JSON 库：fastjson2 → Jackson 2（**已落地，影响实现方式不影响契约**）

配置的 Maven 镜像（aliyunmaven，`mirrorOf=*`）在离线与在线两种模式下都无法解析 `com.alibaba:fastjson2`
（本地缓存来自 central/aicai-repo，镜像缺该构件）。项目已依赖 Jackson（MyBatis-Plus 的 JacksonTypeHandler 亦基于它），
因此改用 Jackson 2 树模型（`ObjectNode`/`ArrayNode`），不新增依赖。
配套约束：**跨 HTTP 边界的 DTO 字段一律用普通 Java 类型**（如 `ArtifactPatchesReq.patches` 为 `Object`），
在服务层用 `JsonSupport.toArray/toObject` 转树——因为 Spring Boot 4 的 HTTP 消息转换器是 Jackson 3（`tools.jackson`），
不能把 Jackson 2 的 `JsonNode` 直接交给它。响应的 `content` 字段统一转成 Map/List 返回（非字符串、非节点对象）。

### D2 网关不支持 WS upgrade（**需用户决策，未自行改网关**）

已实证：网关是 **Spring Cloud Gateway Server WebMVC**（servlet 版，`spring-cloud-gateway-server-webmvc:5.0.3`），
其 jar 内**没有任何 websocket / upgrade 相关类**，且内置 `RemoveHopByHopRequestHeadersFilter` 会剥离
`Connection`/`Upgrade` 等逐跳头——**WS 握手无法穿过该网关**。

影响：`ws://localhost:8080/api/act/ws/chat` 不通；`ws://localhost:8082/api/act/ws/chat` 已验证可用。
可选方案（择一，需用户确认后再动网关）：
1. 前端 WS 直连 8082，HTTP 仍走网关（改动最小，需开放 8082 端口的浏览器可达性/安全域名）；
2. 网关改用 reactive 版（`spring-cloud-starter-gateway`）以支持 WebSocket 路由（改动最大，影响既有路由配置）；
3. 在 Nginx/前置代理上为 `/api/act/ws/` 单独做 upgrade 转发（不改网关代码）。

**推荐（2026-09-18）**：**方案 1 的改良形态——前端同源代理**。
即浏览器只访问前端自身源：开发期用 Vite `server.proxy` 把 `/api`→网关 8080、`/api/act/ws`（`ws:true`）→8082；
生产期由承载 SPA 的 Nginx 做同样转发（upgrade 透传）。理由：

- 不动共享网关（不牵连 SpeechTraining 路由），零后端风险；
- 浏览器侧只有**一个源**：无跨域、日后上 HTTPS 也不会出现 `https` 页面连 `ws://` 的混合内容阻断；
- 不额外向浏览器暴露 8082；
- 可顺带把 HTTP 也收敛为同源，从而有机会收紧网关现在 `Access-Control-Allow-Origin: *`（网关 CorsConfig 现状）这一过宽配置。

若坚持"网关必须是唯一入口"（统一鉴权/限流的前提），则**方案 2（reactive 网关）才是官方支持的做法**，
我可以实施，但需要明确授权改网关（配置键需从 `spring.cloud.gateway.server.webmvc.routes[i]`
迁到 reactive 形式，且两条路由都要回归）。

**多实例前提（无论选哪个方案）**：`WsSessionRegistry` 是进程内存注册表，同一会话的多端连接若被负载均衡
分到不同实例，事件只到达同实例的连接。单实例部署无影响；多实例需**粘性会话**（按 sessionId 或 ip_hash）
或引入 Redis pub/sub 广播。当前 K8s/多实例部署方案未定，需一并考虑。

### D4 生成完成事件的 content 粒度 → **已按"渐次出现"落地（2026-09-18 用户确认）**

需求 FP-33 要求"artifact-generated in_progress 到达时右面板对应 Tab 数据渐次出现"。
原实现是单次 blocking 工作流调用，拿不到部分产物，只能"完成后一次到位"；现改为**流式**：

- `DifyWorkflowClient.runStreaming`：`response_mode:"streaming"`，逐行消费 SSE；
- `DifyWorkflowEventParser`（纯函数、可单测）：识别 `node_finished` / `workflow_finished` / `error`，
  并在 `workflow_finished` 未带 outputs 时**兜底取"携带 artifact_json 的聚合节点输出"**（版本差异容错）；
- 按**输出变量名**识别段（不依赖节点 id/标题，DSL 改名不受影响）：
  `scenes_json` → 场景段；`profiles_json`/`iceberg_json` → 画像+冰山段；
- 每段完成：`ArtifactService.mergeGeneratedPartial` 把中间产物**增量合并**进工作区 artifact
  （只覆盖该段产出的顶级字段，materials 永不被覆盖），随后推
  `artifact-generated {status:"in_progress", content:<当前全量 artifact>, stage:<段标题>}`；
- 流结束：最终产物做 schema 校验（失败重试 1 次）→ `replaceGenerated` 整体落地 → 推 `completed` + 全量 content；
- 超时策略：blocking 的"请求超时"改为**看门狗关流**（避免长响应把生成线程挂死）。

**可见的推进节奏**：受理（in_progress，无 content）→ 场景段就绪（in_progress + 场景单元 Tab 可渲染，
维度/案例暂空）→ 画像+冰山段就绪（in_progress）→ 完成（completed，含维度权重）。
**取舍**：中间产物会真实落到工作区（而非只发事件），这样事件与 §2.2b 的 artifact 拉取始终一致；
代价是生成中途失败时工作区会残留已生成的部分内容（与"渐次出现"的预期一致，前端按 failed 事件提示重试）。

### D5 异步生成结果独立成轮推送

`generate_theme`/`generate_cases` 的**受理事件**（in_progress）由工具端点同步推入当前对话轮次；
但 `completed`/`case-generated` 在 Dify 轮次早已 `session-finish` 之后才到达，无法再挂进原助手消息，
因此实现为"事件发布器自动开一个短轮次"（session-start → message-start → data part → session-finish）
并单独落一条助手消息。效果：右面板实时更新、历史可重放；代价是消息流里会多出一条只含事件卡片的助手消息。

### D6 data part 的 JSON 不做碎片化切分

线上逐 token 切分 data_delta；本项目"一个 bizType 事件 = 一个 data part = 一个 data_delta"，
前端在 part-end 整体解析即可（与 02 §8"翻译器保证单个 data part 的 JSON 完整性"一致）。

### D7 发布完成后案例与编译产物按 sort_order 重挂新版本

`copyUnitsToVersion`（既有保存流程的复制逻辑）会为新版本生成**新的单元行 ID**，
若只复制版本而不重挂，案例与编译产物会指向旧版本单元行。因此在发布收尾时按 `sort_order`
建立"旧单元行→新单元行"映射，把 `act_case_script`/`act_drill_script` 的 `version_no` + `scenario_unit_id` 一并重挂。
这样 `script-progress`（按当前版本统计）在发布前后口径一致，回滚到旧版本也不受影响。

### D8 无案例时的发布行为

已确认内容但案例数为 0 时，`total=0` 会让 `progress=round(completed/total*100)` 除零。
实现为：无案例也走完发布流程（照样新建版本），返回 `status=3`、`progress=100`。

### D9 确认时的主题冗余同步范围

artifact 里**不含主题名称/描述**（名称由 create_topic 维护），因此确认落库同步的是
`customer_profile_count`（画像真实值）+ `conversation_id`（会话绑定）+ `updated_at`；
名称/描述由 create_topic 同时写 `act_theme` 与当前 `act_theme_version` 行。

action 帧本身无正文，而 Dify 需要一个 query 才能生成开场白，故固定传 `开始会话`（常量 `SESSION_START_QUERY`）。

安全约束要求服务端出站请求拒绝环回/私有/保留地址，但 Dify 自建实例就在内网 `10.10.166.81`。
实现为"默认拒绝 + 显式开关"：`dify.allow-private-host=true` 时放行私有网段，

### D19 multipart 上限未对齐（真实踩坑，已修）

**现象**：上传 2.65MB 的 PDF 报 `code=500 服务器内部错误`。

**原因**：Spring multipart 默认上限是 **1MB/文件**，在应用层自己的 `assistant.file-max-size-bytes`（50MB）

小文件冒烟测试（1KB/470B）覆盖不到，是拿真实 2.6MB 材料才暴露的。

**修复**：
1. 显式对齐两条上限：`spring.servlet.multipart.max-file-size=50MB`、`max-request-size=50MB`（与 `assistant.file-max-size-bytes` 一致）；
2. 为 `MaxUploadSizeExceededException` 增加专用 handler，返回 `code=1 上传文件超过大小上限，请压缩后重试`（不再报 500）；
3. 加防回归测试 `MultipartLimitConfigTest`：断言 multipart 上限 ≥ 应用层上限 ≥ 2.6MB（03 文档示例文件大小）。

**验证**：2.65MB PDF 上传成功并解析（提取 1642 字，0.8s）。

### D21 编排智能体当前不可用：应用类型错配 + 缺 query/结束节点（2026-09-18 实测）

**现象**：对话主入口调不通。审计日志里编排调用全部是
`Dify 对话调用失败：HTTP 400 {"code":"not_chat_app","message":"Please check if your app mode matches the right API route."}`。

**取证**（`scripts/dify-app-check.mjs` + `scripts/dify-orchestrator-probe.mjs`）：

| 检查 | 结果 |
|------|------|
| `GET /v1/info`（orchestrator-key） | 《自由演练设计助手-side_free》**mode=workflow**（不是 `agent-chat`） |
| `POST /v1/chat-messages` | **400 not_chat_app** —— 工作流型应用不能走对话接口 |
| `POST /v1/workflows/run` | 200，但 **最终 outputs = `{}`**（Agent 节点本身跑成功了，输出 `text,usage,files,json`） |
| 开始节点输出变量 | `theme_status, artifact_summary, material_summary, sys.files, sys.user_id, sys.app_id, sys.workflow_id, sys.workflow_run_id, sys.timestamp` |

由上述事实得出三个问题（都在 DSL/应用侧）：

1. **应用类型是 workflow**，而 Java 走的是对话型接口 → 必然 400。原设计（04a）是 `mode: agent-chat`。
2. **没有结束节点**：图里只有 `start → agent`，Agent 的回答 `text` 取不出来（实测 outputs 为空），
   所以即便按工作流调用也拿不到任何回答。
3. **用户消息进不来**：开始节点只有三个摘要类变量，Agent 节点的 `query` 被绑成
   `{{#start.theme_status#}}{{#start.artifact_summary#}}{{#start.material_summary#}}`（全是上下文，没有用户输入），
   因此这个形态**无法承载多轮对话**。
4. （附带）工具参数 `traceId`/`sessionId` 在 `agent_parameters` 里是 `auto: 1`，即**由模型自己编值**；
   且授权型应用实测**没有 `sys.trace_id`**（start 输出里没有它），而 04a 的对接要点依赖它定位会话。

**修复方案（推荐 A，Java 零改动）**

- **A：把该应用改成对话型**。两种都行，且现有 Agent 节点内容几乎可原样保留：
  - **Chatflow（advanced-chat）**：开始节点自带用户输入 `query`，`/v1/chat-messages` 可用，
    `conversation_id` 原生多轮；再补一个「回答/结束」节点输出 Agent 文本即可；
  - **Agent（agent-chat）**：直接按 04a 的 DSL 导入，`sys.trace_id` 可用，工具参数按 04a 绑定。
  Java 侧无需改动（`DifyAgentClient` 对两种模式都兼容：SSE 的 `agent_message` 与 `message` 事件都已处理）。

- **B：坚持用 workflow**（需双方改动）：开始节点加 `query`（用户消息）与 `session_id`/`trace_id` 输入；
  Agent 节点 `query` 绑到 `{{#start.query#}}`；**新增结束节点**输出 Agent 的 `text`；工具参数绑到
  `{{#start.trace_id#}}`/`{{#start.session_id#}}`（workflow 无 `sys.trace_id`）；多轮需 Java 把最近 N 轮历史
  作为输入传入（Java 侧需加代码，因为 workflow 无原生会话记忆）。

**Java 侧同步加固（已完成）**：工具端点会话定位改为 **traceId 优先**——因为 DSL 若把 `sessionId` 设为 `auto`，
模型会编造一个 ID；实现仅在 traceId 定位不到时才回退到入参 sessionId，**且回退时必须校验该会话真实存在**
（`AssistantToolServiceImpl.resolveSessionId`，新增 5 例单测覆盖）。

**复查（2026-09-18 晚，用户补了结束节点后重跑探针）**：

| 检查 | 结果 |
|------|------|
| 结束节点 | ✅ 已补（start → agent → end 输出 `agent.text/files/json/usage`），`workflows/run` 的 outputs **不再为空** |
| `mode` | ❌ 仍是 `workflow` → `/v1/chat-messages` 仍 **400 not_chat_app** |
| 最终 `text` | ❌ 是 `Maximum iteration limit (12) reached. Cannot call tool 'tool_name'. Please consider increasing the iteration limit.` |
| `json`（工具调用记录） | 出现 `create_topic` 调用，action_input 里是占位文案（"待用户输入行业、对象与目标后自动建题"） |
| 未声明输入 | ✅ `workflows/run` **容忍未声明输入**（实测传了未声明的 `session_id`/`trace_id`/`query`，未报错） |

**为什么打满迭代**：开始节点仍没有**用户消息**输入，agent 的 `query` 只绑了三个上下文摘要
（`theme_status`/`artifact_summary`/`material_summary`），模型拿不到用户说的话 → 反复试探性调用工具，
直到 12 轮上限，最后把"迭代超限"当作回答返回。
叠加因素：workflow 里没有 `sys.trace_id`（实测开始节点输出了 `sys.workflow_run_id` 等但没有 `sys.trace_id`），
工具参数 `traceId` 渲染为空、`sessionId` 又是 `auto`（模型自编）→ 我的端点按设计拒绝定位（不写错会话），
于是工具持续返回错误，进一步促使其重试。

**仍需处理（两件，缺一不可）**：
1. **开始节点增加"用户消息"输入**（Chatflow 里是自带的 `sys.query`；workflow 里需自建 `query` 变量），
   agent 节点的 `query` 绑到它；
2. **确认应用类型**：改 Chatflow/Agent（推荐，Java 零改动、原生多轮、`sys.trace_id` 按 04a 可用）；
   或保持 workflow（则 Java 改走 `workflows/run`、工具参数改绑开始节点变量（可由 Java 作 inputs 传入，已实测容忍）、
   多轮历史由 Java 传入）。另建议 `maximum_iterations` 从 12 提到 15~20。

**为何校验没拦住**：03 §3.5 的校验规则只覆盖 scenarios / dimensions / iceberg 六层存在性 / cases 字段，
**没有画像条数规则**，所以"画像为空"属规则内的合法产物（`iceberg` 六层键都在，只是数组为空）。
冒烟脚本按 FP-36 的意图（画像 2~4 个）做了断言，因此能把它暴露出来。

   明确"禁止返回空数组"；也可换更大参数模型或商用 API（key 配置化，Java 不用改）。

## 7. 2026-09-21 两个线上缺陷的定位与修复（方案 2A + 1A + 1C）

用户报两个现象：①文件解析卡片一直转圈，而助手早已把核心目标与关键知识点输出完；②WS 经常连接超时
（日志 `WS pong 超时（80001ms 无应答），关闭连接 sessionId=2101843708978585602`）。以下结论均以库内时间戳与
日志取证，不用推断充当事实。

### 7.1 现象①主因：解析与生成共用线程池（修 1A）

**取证**：
- 该会话 `status=0`（解析中）卡片落库 01:19:52，对应的 `status=1` 完成事件落库 01:36:20 —— **相差 16.5 分钟**；
- 而这份材料本身（2.6MB PDF、提取 1642 字）用一次性探针直跑 Tika 只要 **2228ms**；
- 同期该会话在跑主题生成：一次 `generate_theme` 派生 5 个场景任务，单任务实测 150~600 秒，
  全部提交到同一个 `generateExecutor`（core=2 / max=4 / queue=64）。

**结论**：卡片不是"解析慢"，是**根本没轮到它开始解析**。另外 `ThreadPoolTaskExecutor` 先填队列再扩线程，
queue=64 使 max=4 永远不可达 → 该池实际只有 2 个槽。用户看到的"核心目标与关键知识点"来自另一轮生成，
与这条解析卡不是同一件事，所以出现"话都说完了它还在转"。

**修复**：`AssistantProperties` 增 `parsePool`（core=2/max=4/queue=64）、`AssistantExecutorConfig` 增 `parseExecutor` bean、
`AssistantMaterialServiceImpl.acceptParse` 改投 `parseExecutor`。解析 / 生成 / 发布三池互不影响。

### 7.2 现象②：业务帧占住容器读线程，心跳自己把连接踢了（修 2A）

**取证**（同一会话日志时间线）：09:22:13 最后一次 pong → 09:22:29 本轮开始（Dify 流式）→
09:23:33 `pong 超时（80001ms）` 主动关闭 → 09:25:47 落库"抱歉，本次回复出现异常：java.io.IOException: closed。请重试。"

**原因**：`TextWebSocketHandler.handleTextMessage` 跑在 Tomcat 该连接的**读线程**上，而一帧聊天会同步阻塞到
Dify SSE 流结束（`agent-timeout-ms=300000`）。读线程被占 → 这条 TCP 上的入站帧（含客户端 pong）不再被读取 →
"最后 pong 时间"冻结 → 80 秒预算一到服务端自己踢掉连接，本轮后续写帧即 `IOException: closed`。
客户端完全无辜，且**回复越长越容易被杀**，与"经常超时"一致。

**修复**：
- 新增 `WsInboundDispatcher`：按 sessionId **分道**——道内串行（协议里 part 序列不能交错）、跨会话并行；
  工作线程 `assistant.ws.inbound-pool-size`（默认 8），单会话等待队列上限 `inbound-queue-per-session`（默认 20），
  超限拒收并回 `session-finish{error:"服务繁忙，本条消息未能受理，请稍后重试"}`（宁可明确拒也不无界堆内存）。
- `WsChatHandler.handleTextMessage` 只做三件事：JSON 解析失败记 warn 后忽略（**行为变化**：不再回错误帧，
  与 `handleFrame` 对未知帧"忽略"的口径统一）、`pong` 就地记账（毫秒级）、其余交派发器。
- 未采纳 2C（抬高 pong 超时）：治标，且长轮次下真正的问题是读线程被占而非预算太短。

### 7.3 现象①的补偿：丢帧时卡片不再永久转圈（修 1C）

1A 后仍有一处残留风险：`status=1` 完成事件是**一次性推送、不重试**，推送瞬间没有活跃连接
（心跳误杀、刷新页面、断网）就会永久丢帧。前端 `useAssistantStore` 增加兜底：
- 见到 `status=0` 卡片即按 5s 轮询 `GET /sessions/{id}/materials`（上限 60 次）；材料行只在提取成功后才写库
  （`runParse` 成功分支才 `persist`），所以"列表里出现这个 fileId"就是完成的确证，据此**就地**把卡片改成完成态，不新增气泡；
- 等待集合变化时重置计数（新上传不该被老文件的次数预算拖累）；
- 轮询用尽仍未见到（解析失败不写材料行 / 根本没受理）→ 收口成"服务端确认超时"终态，同样停转；
- 同 `context_id` 已有完成卡时丢弃重复卡（重连后历史重放与实时事件并存的场景）；`reset()` 停轮询。

## 8. 2026-09-21 追加：空气泡复发与 Dify 调用失败根因（前端回收 + 后端源头减量 + 文案如实）

用户第二轮报的两件事：① 聊天框重复出现"只有助手头像、没有输出"的空气泡（§6.3 修过一次又复发）；

### 8.1 空气泡为什么修过一次又复发（两条不同的产生路径）

- §6.3 修的是**服务端只发了 `message-start`、一个 part 都没到**的空气泡，判据 `streaming && blocks.length===0`，
  清理时机固定在 `session-finish`。这条路径至今有效。
- 这次是**另一条路径：卡片先渲染出来、后被归并掉**。后端每推一条 `in_progress` 进度就 `pushStandalone`
  落一条"只含一张进度卡"的助手消息；前端 `mergeGeneratedCard` 按 `params.id` 把它们归并进第一张卡并
  `splice` 掉重复块，但**没有删除被清空的宿主消息**，`ChatColumn.vue` 又对 `store.messages` 无条件
  `v-for` 渲染 → 一条消息只剩头像。历史重放走同一归并逻辑，所以刷新后照样复现。
- 取证（会话 `2101879716243771394` / themeId `2101880270428770306`，12:59 拉的 `/messages?pageSize=1000`）：
  122 行消息、118 条助手，其中 **113 条各含且仅含一张 `biz-side-manage-artifact-generated` 卡**
  （in_progress 83 / failed 26 / completed 4；全库该 bizType 块共 152 个）。
  即一次生成的进度点全部独立成了消息行。

### 8.2 修法

- 前端 `useAssistantStore.dropEventBlock`：`splice` 之后若宿主消息 `blocks.length===0 && !streaming`，
  从 `messages` 中移除并清掉 `messageRoundTrace` 条目（`streaming` 中的不能删——后续 `part-*` 还要往它身上落）。
  `mergeGeneratedCard` 改为复用 `dropEventBlock`（原先自己内联了一段 `splice`，正是这次漏删的直接原因）。
- 前端 `loadHistory` 的重放循环改为遍历 `[...messages.value]` **副本**：回收会让活数组左移，
  直接遍历活数组会漏掉相邻消息（事件不再被重放）。
- 前端 `ChatColumn.vue`：加 `visibleMessages` 渲染层兜底过滤（0 内容块且不在流式 ⇒ 不画气泡），
  `tailSignal` 同步按可见消息计算滚动信号。
- 后端 `AssistantEventPublisher`：落点由两种扩为三种（见 02 §5.2）——新增 `pushTransient`，
  `pushStandalone` 加 `persist` 开关。`ThemeGenerationServiceImpl` 的**受理 in_progress**（`accept`）与
  **分段进度 in_progress**（`pushInProgress`）改走 `pushTransient`；`completed`/`failed`/`case-generated`/
  `parse-file` 等结果类事件仍逐条落库。
- 已落库的 113 条进度/结果消息**按用户决定不清理**：前端回收后它们不再渲染成空气泡。

### 8.3 Dify 调用失败的根因（结论：在 Dify 侧模型执行链路，不在 Java）

分层取证：

1. **Dify API 层健康**：三个 app key `GET /v1/parameters` 全 200（0.1~0.2s）→ key、路由、应用存在性都没问题。
2. **绕开本应用直接流式调主题生成工作流**：`开始` 节点 0.3s succeeded → `①生成场景列表` 只有 `node_started`，
   **之后 150s 无任何事件** → 卡死点在 LLM 节点内部，不在我们的 HTTP 调用方式上。
3. **模型推理网关 `10.10.166.81:9901`**：TCP 可连、`/health` 200、`/v1/models` 401 → 进程活着但不干活。
4. **Dify 自己给出的原因**：早期日志 `[models] Server Unavailable Error, HTTPConnectionPool(host='10.10.166.81', port=9901): Max retries exceeded ... Connection refused`；本轮该会话失败卡上的 error 是
   `Dify 工作流执行失败：Request to Plugin Daemon Service failed-500`。

⇒ 根因是 **Dify plugin-daemon ↔ 模型运行时（9901）这一段不可用**（D20 未闭环的同一个问题），
不是 Java 客户端、不是超时参数、不是网络抖动。恢复动作在 Dify 部署侧，本模块改不了。

**我们这一侧放大问题的缺陷（已修）**：`DifyAgentClient.stream` 的看门狗把原因写进 `errorHolder[0]`
（"Dify 响应超时"）后关流，`BufferedReader` 的流式读取抛出的是 `UncheckedIOException(IOException: closed)`，
而 catch 列表只有 `BizException / InterruptedException / IOException` → 异常逃到主链路兜底
（`AssistantChatServiceImpl:166`），用户在聊天框看到
`抱歉，本次回复出现异常：java.io.IOException: closed。请重试。`。
`DifyWorkflowClient` 早就为同一个坑加了 `UncheckedIOException` 翻译（其注释里记着"实测踩过"），对话侧当时漏了。

修法：

- catch 改为 `IOException | UncheckedIOException`，**优先使用看门狗记下的原因**；看门狗文案改为
  "回复超时（300 秒未完成），请重试或简化提问"（秒数按 `assistant.dify.agent-timeout-ms` 算）。
- 新增 `rootMessage(Throwable)`：包装异常取根因消息，避免把 `java.io.UncheckedIOException: ...` 类名甩给用户。
- `safeFailAndFinish`：原因里已含"重试"时不再叠加兜底的"。请重试"，否则输出"…请重试。请重试。"。
