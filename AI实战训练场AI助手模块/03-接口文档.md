## 1. 通用约定

- HTTP Base URL：`http://localhost:8080/api/act`；统一响应 `{code, message, data}`，code=0 成功
- 时间：`yyyy-MM-dd HH:mm:ss`；ID 一律字符串
- WS：`ws://localhost:8080/api/act/ws/chat?sessionId={id}`（网关需放行 WS upgrade）
- 枚举：

| 枚举 | 值 |
|------|-----|
| artifact.status | working / confirmed |
| case_script.status | draft / compiled / failed |
| 主题 status | 沿用既有：0草稿 1发布中(初始化中) 3已发布 4已暂停 5已结束 |
| 材料文件类型 | ppt/pptx/doc/docx/pdf/txt/md |

## 2. HTTP 接口

### 2.1 FP-31 建立/查找会话

- `POST /api/act/assistant/sessions`
- **请求**：`{ "themeId": "1948..." }`（可空=新建）
- **响应**：

```json
{ "code": 0, "data": {
  "sessionId": "a3f8...",
  "themeId": "1948...",
  "isNew": true,
  "artifact": { "artifactId": "7556...", "versionNo": "1", "status": "working",
                "content": { "...artifact JSON 全量，无产物时 null..." } }
} }
```

> themeId 非空且已有会话 → 复用（isNew=false）；artifact 返回工作区版本（无工作区则 confirmed 最新）。

### 2.2 FP-31 历史消息（cursor 分页）【线上同款语义】

- `GET /api/act/assistant/sessions/{sessionId}/messages?limit=1000&cursor=`
- **响应**：

```json
{ "code": 0, "data": {
  "messages": [
    { "dbId": "213c...", "id": "3fe4...", "sessionId": "a3f8...", "role": "user",
      "content": [ { "type": "text", "text": "开始生成", "extendedData": {} } ],
      "sender": { "id": "admin", "name": "管理员", "avatar": "" },
      "createdAt": "2026-09-17 14:39:46" }
  ],
  "pagination": { "limit": 1000, "hasNextPage": false, "nextCursor": "" }
} }
```

> 消息按时间正序返回；data 块（事件）原样存储原样返回，前端重放渲染。

### 2.2b FP-33 拉取当前 artifact（右面板兜底刷新）

- `GET /api/act/assistant/sessions/{sessionId}/artifact`
- **响应**：与 2.1 的 artifact 字段一致（工作区版本；无产物返回 `{ "code": 0, "data": null }`）
- 使用时机：进入会话、重连后、事件丢失兜底刷新。

### 2.2c 会话材料解析结果（2026-09-20 新增，"文件解析完成"卡片展开用）

- `GET /api/act/assistant/sessions/{sessionId}/materials`
- **响应**：

```json
{ "code": 0, "data": { "materials": [
  { "id": "<材料行 id>", "fileId": "<act-files 下文件名>", "name": "材料.pdf",
    "fileType": "pdf", "fileSize": 2785280, "visibility": 1,
    "extractLength": 18422, "truncated": true, "preview": "提取文本前 2000 字…" }
] } }
```

- 字段语义：`extractLength` 为提取全文长度；`preview` 固定截断到 **2000 字**（`MaterialBriefResp.PREVIEW_CHARS`），`truncated=true` 表示被截断；`visibility` 1 学员可见 / 0 内部可见。
- 空会话/无材料返回 `{ "materials": [] }`（**不报错**），前端展开区据此提示"没有可展示的解析内容"。
- 使用时机：仅当用户点开"文件解析完成"卡片的**查看解析结果**时按需拉取（不在消息流里内联全文）。
- 提取文本为空（扫描件 / 图片型 PDF / 空文件）时 `extractLength=0`、`preview=""`，前端提示"未解析出文本"。
- **第二个用途（2026-09-21 起）：解析卡丢帧兜底的判据源。** 完成态事件（`status=1`）是一次性 WS 推送、不重试，
  丢帧时卡片会一直转。后端材料行只在文本提取成功后才写库（`AssistantMaterialServiceImpl.runParse` 成功分支才 `persist`），
  所以"本会话材料列表里出现了这个 fileId"就是解析已完成的确证。前端 `useAssistantStore` 见到 `status=0` 卡片即按 5s
  间隔轮询本接口，最多 60 次（约 5 分钟）：查到即把卡片就地改成完成态；轮询用尽仍未查到（解析失败不写材料行）
  则把卡片收口成"服务端确认超时"终态——两条路径都不新增气泡，也不让卡片停在转圈态。

### 2.3 FP-42 文件上传（含材料解析触发，2026-09-18 补充）

- `POST /api/act/assistant/files`（multipart/form-data：`file`，可选查询参数 `sessionId`）
- **响应**：`{ "code": 0, "data": { "fileId": "3a20...", "name": "订单运营部职能介绍.pptx", "fileType": "pptx", "fileSize": 2638848 } }`
- 错误：`code=1 不支持的文件类型`（前端也做前置拦截）
- **带 `sessionId` 时**：上传成功后**异步触发解析**（本地 Apache Tika 提取 → 规则摘要 → 落 `act_ai_material`
  → 有主题则追加进工作区 `artifact.materials`），并以 `biz-common-parse-file` 事件推送两态
  （0 解析中 → 1 完成，详见 §3.4）；不传 `sessionId` 则仅落盘返回 `fileId`（与旧行为一致）。
- 上传本身不阻塞：接口立即返回，解析在后台线程池执行。
  **该池是解析专用的 `parseExecutor`（`assistant.parse-pool.*`，默认 core=2/max=4/queue=64），不与生成类任务共用**
  （2026-09-21 起；共用时一次主题生成会把解析排到十几分钟后，见 07 §7.1）。本地 Tika 实测 2.6MB PDF 提取 1.3~2.2 秒。

### 2.4 FP-32 语音识别（ASR）

- `POST /api/act/assistant/asr`（multipart/form-data：`audio`，16kHz WAV）
- **响应**：`{ "code": 0, "data": { "text": "希望快速上手，针对于新入职人员" } }`
- 错误：识别 <2 字返回 `code=1 请重试`

### 2.5 FP-35~37 Dify 工具端点（内网，供 Dify 回调）

> Dify 以 "API 工具" 方式调用。路径前缀 `/api/act/internal/tools`，仅允许内网来源。响应为工具结果（Dify 把 data 作为工具观察结果喂回模型）。所有端点执行业务后**主动向会话 WS 推送对应事件**（见 §3.4），事件推送不依赖本响应。

#### 2.5.1 create_topic（FP-39）

- `POST /api/act/internal/tools/create_topic?traceId=xx&sessionId=xx`
- **请求**：

```json
{ "topic": "订单运营部职能培训设计", "description": "基于订单运营部职能介绍文档……" }
```

- **响应**：`{ "code": 0, "data": { "themeId": "0e65...", "created": true } }`
- 行为：无主题→建草稿（默认设置）+回填会话；有主题→改名/描述；推 `biz-side-manage-topic-changed`

#### 2.5.2 update_artifact（FP-35）

- `POST /api/act/internal/tools/update_artifact?traceId=xx&sessionId=xx`
- **请求**（JSON-Patch 数组，op 当前仅 full_replace）：

```json
{ "patches": [ { "op": "full_replace", "path": "/materials",
    "value": [ { "id": "3a20...", "name": "订单运营部职能介绍", "fileType": "pptx",
                 "fileSize": 2, "fileSizeUnit": "M", "visibility": 1 } ],
    "reason": "Replace all materials" } ] }
```

- **响应**：`{ "code": 0, "data": { "versionNo": "1" } }`；推 `biz-side-manage-artifact-updated`

#### 2.5.3 generate_theme（FP-36）

- `POST /api/act/internal/tools/generate_theme?traceId=xx&sessionId=xx`
- **请求**：`{ "goal": "提升订单处理规范与异常应对能力", "audiences": ["订单运营专员"], "materialSummary": "…", "keepExisting": false }`
- **响应**（立即返回受理，生成异步）：`{ "code": 0, "data": { "accepted": true } }`
- 异步完成推 `biz-side-manage-artifact-generated`（in_progress→completed 或 failed）

#### 2.5.4 generate_cases（FP-37）

- `POST /api/act/internal/tools/generate_cases?traceId=xx&sessionId=xx`
- **请求**：`{ "scenarioIds": ["461d...", "b2c3..."], "difficulty": 2 }`（scenarioIds 空=全部场景；difficulty 0=由智能体按场景自定）
- **响应**：`{ "code": 0, "data": { "accepted": true } }`
- 每场景完成推 `biz-side-manage-case-generated`；全失败推 failed 事件

### 2.6 FP-41 发布与进度

- `POST /api/act/admin/theme/{id}/publish`（无 body）
- **响应**：`{ "code": 0, "data": { "status": 1, "totalCases": 4 } }`
- 错误：`code=1 请先在 AI 助手中确认内容` / `code=1 当前状态不允许发布`
- `GET /api/act/admin/theme/{id}/script-progress`

```json
{ "code": 0, "data": { "total": 4, "completed": 2, "failed": 0, "progress": 50, "status": 1 } }
```

> status 为主题当前状态（1=发布中/3=已发布）；progress=round(completed/total*100)。前端 status=1 时 5s 轮询，变为 3 停止。
>
> **`total` 是"实战案例数"**（按 `act_case_script` 当前版本统计），**不是场景单元数**。主题下没有案例时后端无需等待，直接置 `status=3` 并返回 `total=0, progress=100`——前端文案必须区分口径：实测把它写成"0 个场景全部就绪，主题已发布"会让用户以为 6 个场景单元没发布（2026-09-20 修复）。

- `POST /api/act/admin/theme/{id}/publish/retry`（仅失败项重试）

## 3. WebSocket 协议规范【线上同款】

### 3.1 连接与心跳

- URL：`/api/act/ws/chat?sessionId={id}`；同一会话允许多连接（多端）
- 心跳：服务端发 `{"type":"ping","ts":1789627134712}`，客户端 20s 内回 `{"type":"pong"}`；超时服务端关闭连接，前端指数退避重连
- **入站帧的线程模型（2026-09-21 起）**：`pong` 在容器读线程上直接处理（毫秒级，保证心跳始终能被记账）；
  业务帧（chat / action）交给 `WsInboundDispatcher`——按 sessionId 分道、道内串行、跨会话并行，读线程立即返回。
  一帧聊天会阻塞到 Dify 流式回复结束（可达数分钟），若占住读线程，本连接的 pong 收不进来，
  80s 后连接即被心跳误杀（旧行为，见 07 §7.2）。
- **入站排队上限**：单会话等待中的帧数上限 `assistant.ws.inbound-queue-per-session`（默认 20），
  超限直接拒收并回一帧 `session-finish`（`data.error="服务繁忙，本条消息未能受理，请稍后重试"`），
  避免慢会话把内存堆满；派发线程池本身另有 256 的全局队列，拒收时打 error 日志。

### 3.2 客户端 → 服务端

**发消息**（type=chat）：

```json
{
  "type": "chat",
  "payload": {
    "message": {
      "id": "6f4d3410-0656-4e9d-937f-504946d453ac",
      "role": "user",
      "content": [
        { "type": "text", "text": "开始生成", "extendedData": {} }
      ],
      "sender": { "id": "admin", "name": "管理员", "avatar": "" }
    }
  },
  "traceId": "1b2aa3fe78a44840865ef9ae1a1cb293",
  "spanId": "1190dc8ed16a4548"
}
```

content 块类型：

| type | 结构 | 用途 |
|------|------|------|
| text | `{type, text, extendedData}` | 普通消息 |
| file | `{type, file:{uri:fileId}, extendedData:{name,fileType,fileSize,target,source:2}}` | 已上传文件入会话 |
| data(action) | `{type, data:{type:"action", actionName, params}}` | common-session-start（重进自动发）/ biz-side-manage-confirm（确认按钮）/ biz-side-manage-update-material（材料学员可见开关） |

action 定义：

| actionName | params | 时机 |
|-----------|--------|------|
| common-session-start | `{sessionId, projectId}` | WS 连接建立后自动发送；新建/恢复会话使用不同开场 query |
| biz-side-manage-confirm | `{id: artifactId, version: N}` | 点击右面板「确认」 |
| biz-side-manage-update-material | `{id: artifactId, version: N, materialId, visibility}` | 右面板「培训材料」Tab 切换「学员可见」开关（visibility：1 可见 / 0 不可见） |

> `biz-side-manage-update-material` 为本次新增（2026-09-17 经用户确认，FP-42 验收项需要）：
> 原线上协议没有前端可用的 artifact 写入通道（§2.5.2 的 update_artifact 标注仅限内网、供 Dify 回调），
> 故沿用 action 机制扩展一条。后端行为：更新工作区 artifact 的 `materials[].visibility`，
> 并推 `biz-side-manage-artifact-updated`（`content: [{op:"full_replace", path:"/materials", value:[...materials]}]`）；
> 前端以该事件回写为准。

**非法入站帧**：payload 不是合法 JSON 时**忽略并记 warn 日志**，不回 `session-finish`（2026-09-21 起，
与 `handleFrame` 内部对未知帧的处理口径统一：旧实现会回一帧错误事件，反而让无关连接被噪音帧打扰）。

### 3.3 服务端 → 客户端（事件流）

每轮对话事件序列（seq 在**单轮内**从 1 递增）：

```
user-message-ack → session-start → message-extra-info → message-start
→ N × [part-start → part-content × M → part-end]
→ session-finish
```

| 事件 | data 关键字段 | 说明 |
|------|--------------|------|
| user-message-ack | userMessageDbId, userMessageId | 用户消息落库回执 |
| session-start | sessionId, traceId, timestamp, seq | 轮次开始 |
| message-extra-info | messageId, extraInfo{taskId, contextId} | 任务上下文 |
| message-start | messageId（助手，`xxx_0` 格式）, sender{id:agentId}, agentMessageDbId, agentMessageCreatedAt | 助手消息开 |
| part-start | index, contentType(text\|data), messageId | part 开（textType 空串、partExtendedData/messageExtendedData 照抄结构） |
| part-content | index, delta, messageId | **text**: `{delta:{type:"text_delta",text:"…"}}`；**data**: `{delta:{type:"data_delta",data:"JSON片段"}}` |
| part-end | index, messageId | part 结束（前端此时解析 data part 完整 JSON） |
| session-finish | sessionId, timestamp | 轮次结束（前端解除输入禁用） |

**示例**（data part 流式）：

```json
{"type":"event","event":"part-start","data":{"index":3,"type":"PART_START","timestamp":"2026-09-17 14:39:01","contentType":"data","partExtendedData":{"partType":"data"},"messageExtendedData":{"version":1},"messageId":"6d51113b..._0","seq":79}}
{"type":"event","event":"part-content","data":{"index":3,"type":"PART_CONTENT","timestamp":"...","delta":{"type":"data_delta","data":"{\n  \"biz"},"messageId":"6d51113b..._0","seq":80}}
{"type":"event","event":"part-content","data":{"index":3,"type":"PART_CONTENT","timestamp":"...","delta":{"type":"data_delta","data":"Type\": \"biz-side-manage-topic-changed\""},"messageId":"6d51113b..._0","seq":81}}
{"type":"event","event":"part-end","data":{"index":3,"type":"PART_END","timestamp":"...","messageId":"6d51113b..._0","seq":103}}
```

**与线上的差异**：part-content 按 80ms 节流聚合推送（线上逐 token）；其余不变。

### 3.4 bizType 事件字典（data part 完整 JSON）

| bizType | 触发 | params 结构 | 前端行为 |
|---------|------|-------------|----------|
| biz-common-parse-file | 文件解析状态 | `{context_id, call_id, content, files:[{id,name,status}]}` status: 0解析中/1完成 | 消息流内联卡片两态 |

> **biz-common-parse-file 落地细化（2026-09-18）**：
> `context_id`/`call_id` 由服务端生成（同一文件的两态事件**共享同一个 `context_id`**，前端据此把"解析中"卡片
> 原地更新为"解析完成"，不要新增一条）；`files[].id` = 上传接口返回的 `fileId`；`content` 为可读文案
> （解析中："正在解析材料《X》……"；完成："材料《X》解析完成（提取 N 字） ：<摘要预览>"）；
> 完成态额外携带可选字段 `summary`（摘要预览，便于前端展示与编排智能体解释）。
> **解析失败不新增 status 枚举**：仍推 `status=1`，在 `content` 中说明失败原因（如"解析失败：TikaException"）。
> 提取引擎为本地 Apache Tika（不依赖 Dify、无 LLM 费用），扫描件 PDF（无文本层）会得到空文本。
| biz-side-manage-topic-changed | 建草稿/改名 | `{explicit:true, topic, description}` | 右面板展开、主题名更新、列表可见 |
| biz-side-manage-artifact-updated | JSON-Patch 更新 | `{id, version, content:[{op,path,value,reason}]}` | 右面板按 path 局部更新 |
| biz-side-manage-artifact-generated | 主题生成 | `{id, version, status, content?, stage?}`：in_progress（content 为当前全量产物的已生成部分）→ completed / failed(+error) | 右面板渐次渲染/完成态/失败提示；**同一 `id` 的多条事件应原地更新同一张卡片，见 §5.2b 前端约定** |
| biz-side-manage-case-generated | 单案例完成 | `{id, jsonArtifactId, scenarioId, subjectId, scriptName, difficulty, status}` | 场景卡+1 案例、案例详情 |
| biz-side-manage-save-success | 确认落库成功 | `{id, version, ex_id: themeId}` | 成功提示、详情页数据刷新 |

> 案例剧本正文（actorPersonality/scriptOpening 等）不入事件流——前端从 artifact 拉取（2.1 响应或新增 `GET /api/act/assistant/sessions/{id}/artifact`）。
>
> **落库与广播（2026-09-21 修订）**：`biz-side-manage-artifact-generated` 的 `in_progress`（受理 + 各分段进度）**只广播、不落库**，
> 刷新后消息流里只重放该次生成的 completed/failed 一张卡；其余事件（completed/failed、case-generated、parse-file、save-success、
> topic-changed、artifact-updated）仍逐条落库。理由与实现见 §5.2、07 §8。

### 3.5 artifact JSON Schema（8 顶级字段）

```json
{
  "materials": [ { "id", "name", "fileType", "fileSize", "fileSizeUnit", "visibility", "fileServId", "fileSource", "targetId" } ],
  "scenarios": [ {
    "id", "name", "audiences": [],
    "businessGoal", "behaviorGoals": [],
    "relatedIcebergElements": { "knowledge":[], "skills":[], "roles":[], "selfConcept":[], "personalities":[], "motives":[] },
    "businessImpact", "failureCost", "coreConflict",
    "failureReasons": [], "difficulties": [],
    "constraints": { "forbidBehaviors": [], "maxTime": 15 },
    "relatedKnowledgeIds": [], "relatedScriptIds": [], "relatedProductProfileArtifactIds": [],
    "caseArtifactIds": [], "cases": [ { "scriptName", "difficulty", "actorName", "actorPosition", "actorCompany", "actorType", "actorPersonality", "actorCommunicationStyle", "scriptBackground", "scriptOpening" } ],
    "dimensionWeights": [ { "dimensionId", "weight" } ]
  } ],
  "customerProfiles": [ { "id", "type", "description", "personalities":[], "decisionFactors":[], "communicationStyle", "painPoints":[] } ],
  "icebergModel": { "visible": { "knowledge":[], "skills":[] }, "hidden": { "roles":[], "selfConcept":[], "personalities":[], "motives":[] } },
  "evaluationCriteria": { "passScore": 70, "dimensions": [ { "id", "name", "description", "criteria" } ], "defaultDimensionWeights": [ { "dimensionId", "weight" } ] },
  "professionalKnowledge": null,
  "productProfiles": [],
  "version": "v1"
}
```

**校验规则（Java ArtifactSchemaValidator）**：scenarios 非空且 4~7 个；每场景 dimensionWeights 非空、引用的 dimensionId 存在于 evaluationCriteria.dimensions 且同场景权重合计=100；evaluationCriteria.dimensions 3~6 个、defaultDimensionWeights 合计=100；cases 内字段非空（scriptName/actorName/scriptBackground/scriptOpening）；icebergModel 六层齐全（可为空数组）。

> **2026-09-18 增补（Java 侧已实现，见 08 文档）**：在原有规则之上增加两条**非空**要求，
> 用于拦住"工作流静默产出空画像/空冰山"的产物（原规则只查"键存在"，空数组算合法，问题会被静默放行）：
>
> - **customerProfiles 2~4 个**（FP-36），且每个画像的 `id`/`type`/`communicationStyle` 非空、
>   `personalities`/`decisionFactors`/`painPoints` 非空数组；
> - **icebergModel 六层非空**：`visible.knowledge`/`visible.skills` 各 ≥6 条，`hidden` 四层各 ≥4 条
>   （与主题生成 DSL 提示词里的条数要求对齐；阈值定义在 `ArtifactSchemaValidator` 常量处，可统一调整）。
>
> 触发该规则时进入既有的"失败重试 1 次"路径：错误信息会拼进 `material_summary` 尾部重跑
> （`【上次输出校验失败：…，请修正】`）；两次都不过则推 `failed` 事件。
> 注意：实测该重试**不是可靠修复手段**（模型是否补上画像不稳定），根治仍需 DSL 侧调整（见 08 文档）。

## 5. 实现期补充说明（编码已落地，与上文不冲突，仅为落地细化）

1. **WS 连接地址**：后端实现于 `ws://<host>:8082/api/act/ws/chat?sessionId={id}`。
   网关（Spring Cloud Gateway Server **WebMVC**）不支持 WebSocket upgrade（无相关实现且会剥离 Upgrade/Connection 逐跳头），
   经 8080 的 WS 握手不通；网关侧处理方案待确认（详见 07-实现说明与偏差记录.md D2）。
2. **异步事件轮次**：`generate_theme`/`generate_cases` 的 **in_progress 受理事件**并入当前对话轮次；
   其 **completed / case-generated** 在原轮次 `session-finish` 之后到达，会开启一个新的短轮次
   （`session-start → message-extra-info → message-start → part(data) → session-finish`）并单独落一条助手消息，
   保证多端实时与历史重放一致。
   **2026-09-21 修订**：`artifact-generated` 的 **in_progress 事件**（受理 + 分段进度）改走"只广播不落库"
   （`AssistantEventPublisher.pushTransient`）——当前轮次还开着时仍并入本轮，轮次已结束时只开一个短轮次广播、
   **不写 `act_ai_message`**。一次生成在消息流里因此只留 completed/failed 一张卡；进度不落库不影响最终状态
   （右面板随时可用 §2.2b 兜底拉取，前端归并逻辑对"只有结果卡"的历史同样成立）。
   `case-generated`、`parse-file`、`save-success` 等结果类事件仍逐条落库。
2b. **主题生成的"渐次出现"**（FP-33，2026-09-18 用户确认）：后端以**流式**方式调用主题生成工作流
   （`response_mode:"streaming"`），每完成一段（场景段 / 画像+冰山段）即把中间产物增量合并进工作区 artifact，
   并推一次 `biz-side-manage-artifact-generated`，`status="in_progress"`、`content` 为**当前已生成部分的全量 artifact**，
   另附可选字段 **`stage`**（该段节点标题，便于前端/日志区分：场景段→画像冰山段→最终）。
   第三段（评估维度）与最终聚合在流结束时一次到位，推 `status="completed"` + 全量 content。
   前端按收到的 `content` 覆盖右面板即可（未生成的 Tab 保持原样）；也可随时用 §2.2b 兜底拉取。

   > **前端约定（必读）：同一个 `params.id` 的 artifact-generated 事件必须"原地更新"，不得新增消息。**
   >
   > 一次生成会推 **3~4 条同 id 的 `artifact-generated`**（受理 → 场景段 → 画像+冰山段 → completed），
   > 它们的语义是**同一份产物的状态更新**，而不是多条独立消息：
   > | 次序 | `status` | `content.scenarios.length` | 说明 |
   > |------|----------|---------------------------|------|
   > | 1 | in_progress | 0 | 受理（尚未产出，0 不是错误） |
   > | 2 | in_progress | 6 | 场景段就绪 |
   > | 3 | in_progress | 6 | 画像 + 冰山就绪（`customerProfiles`/`icebergModel` 有值） |
   > | 4 | completed | 6 | 全量产物（含评估维度与权重） |
   >
   > 处理规则：
   > 1. 以 **`params.id`** 为 key；消息流中已存在同 id 的 in_progress 卡片时，**更新该卡片的 params 并重渲染**，不新增气泡；
   > 2. `params.content` **每次都是"当前全量产物"**，用最新一次整体覆盖即可，不需要前端做增量合并；
   > 3. `status:"completed"` 到达 → 同 id 卡片转为完成态（或收起）；`status:"failed"` → 在同一张卡片上显示 `params.error`；
   > 4. 需要区分"哪一段就绪"时用可选字段 `params.stage`（值为该段节点标题，如 `"解析场景JSON"`），不需要可忽略。
   > 5. `status:"completed"` 到达时，把助手此前说的"正在生成…请稍候"占位句**替换为完成句**：生成是异步受理的（受理即返回），助手不会在完成时补发一条"已完成"，不主动改这句就永远停在"请稍候"（实测踩到）。
   > 6. 维度 `criteria` 是**一整串**（`"优秀(90-100分)：…；良好(70-89分)：…；需改进(<70分)：…"`），渲染前必须拆三档：先按 `[;；\n]` 切，切不出 3 段时按档位标签（优秀/良好/需改进）前视兜底，每段去掉前导标签与尾部标点。把整串塞进"优秀"会让良好/需改进显示"—"（实测踩到，见 07 §6）。
   > 7. **轮次归属用并存集合，不能用单值**：后台事件轮次（生成受理 / 分段 / 完成各起一轮）与智能体轮次会同时存在，单值会被后到的 `session-start` 覆盖，使先到的那一轮 `session-finish` 被误判为"非本轮"而丢弃 → 空气泡永久残留、"正在生成"永不结束。收尾时只清理"本轮自己的"或"全部轮次都结束"的空气泡；用 `loadHistory()` 整体覆盖消息列表必须等最后一轮结束再做，否则会冲掉仍在流式的气泡（后续 part-* 无处可写）。
   >
   > 8. **卡片被归并掉后要回收宿主消息**（2026-09-21 修，见 07 §8）：一条独立事件消息通常只装一张卡，本次卡片按 `params.id`
   >    合并进先前那张以后，本条消息就没有任何内容块了 —— 留着会渲染成"只有头像、没有输出"的空气泡，必须从消息列表删除
   >    （`streaming` 中的除外：后续 `part-*` 还要往它身上落）。渲染层再加一道兜底过滤（0 内容块且不在流式 ⇒ 不画气泡）。
   >    历史重放走同一逻辑，且重放时要遍历消息数组的**副本**——回收会让数组左移，直接遍历活数组会漏掉相邻消息。
   >
   > 验收：一次生成过程只出现**一张**"正在生成…"卡片，计数从 0 递增到实际场景数，最后转为完成态。
3. **data part 粒度**：一个 bizType 事件 = 一个 data part = 一个 `data_delta`（不按 token 碎片化），前端在 `part-end` 整体解析。
4. **message-extra-info 的 extraInfo**：`taskId` 取 Dify `message_end.task_id`，`contextId` 当前为 null（未接 Dify 上下文变量）。
5. **save-success 的 version**：为该 artifact 行的 `version_no`（字符串）；`ex_id` 为主题 ID。
6. **确认落库范围**：写入主题"当前版本号"的行，先删该版本旧行再插（覆盖语义）；
   维度按场景的 `dimensionWeights` 展开为独立行；同步 `customer_profile_count` 与 `conversation_id`。
7. **发布**：无案例时直接完成（`status=3`、`progress=100`）；编译部分失败保持 `status=1`，
   用 `script-progress.failed` + `POST publish/retry` 重试失败项；
   全部成功后新建业务版本并把案例/编译产物重挂到新版本（`versionCount` +1、`currentVersionNo` 指向新版本）。
8. **内部工具端点鉴权**：仅放行内网来源（环回/站点本地/链路本地）；`sessionId` 可缺省，服务端按 `traceId` 回找会话。
9. **文件上传**：仅白名单 ppt/pptx/doc/docx/pdf/txt/md，落盘文件名为服务端 uuid+扩展名（不使用客户端文件名做路径）；
   文档提取（`extract_text`/`summary`）与 `biz-common-parse-file` 事件已按 07 D13 实现：上传带 `sessionId` 时异步解析并推送两态事件。
