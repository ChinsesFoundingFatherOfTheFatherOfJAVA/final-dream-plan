**版本语义（两路径并存，文档级约定）**：

| 路径 | act_theme_version 产生时机 | 说明 |
|------|---------------------------|------|
| 人工：主题设置保存 | 保存时 version+1（已实现） | 不变 |
| AI：确认 → 发布 | 确认只落内容到"当前版本号"的行；发布完成时 version+1 并冗余同步 | 对齐线上"发布=第一版" |

> 实现细节：AI 确认落库写入的是 act_theme.current_version_no 对应的场景单元行（草稿主题 current_version_no=1 起步）。发布完成 → 新建 version 行（复制五表单+场景单元，同既有"保存"的复制逻辑）→ current_version_no 指向新行。已发布主题再次确认 → 直接覆盖当前版本场景行，再次发布再 +1。

## 5. 关键流程

### 5.1 消息处理主链路（WS 收到 chat 帧）

```
1. 解析帧（块类型：text/file/action）→ user 消息落库 act_ai_message
2. 回 user-message-ack
3. 若 action=biz-side-manage-confirm → 走确认流程（5.3），不进 Dify
4. 若 action=common-session-start → 拼装上下文（历史+artifact+材料摘要）调 Dify 编排 Agent（streaming）
5. Dify SSE 事件流 → DifyEventTranslator：
   · agent_message 增量 → 聚合 80ms → part-content(text_delta)
   · 工具调用事件（Dify agent 的事件流含 tool_call）→ 由工具端点侧推送对应 bizType data part（见下）
   · message_end → session-finish
6. 助手完整消息落库（含 data 块）
```

**入站线程模型（2026-09-21 修订）**：上面第 1~6 步**不在容器读线程上执行**。`WsChatHandler.handleTextMessage` 只做两件事——
记账 `pong`（毫秒级，留在读线程）、把业务帧交给 `WsInboundDispatcher`（按 sessionId 分道：道内串行保证同一会话帧序，
跨会话并行；池大小 `assistant.ws.inbound-pool-size`，单会话排队上限 `inbound-queue-per-session`，超限拒收并回 `session-finish` 错误）。
原因：第 4 步的 Dify 流式回复要占住这一帧到 `message_end`（实测 1~5 分钟），读线程被占则该连接的 pong 收不到，
80s 心跳预算一到就被自己踢掉，随后写帧报 `java.io.IOException: closed`（现象与取证见 07 §7.2）。

**Dify Agent 工具调用与事件的时序**：Dify Agent 执行中会先发 `tool_call` 事件再回调工具端点。Java 工具端点执行业务时**主动**向该会话所有 WS 连接推送 bizType data part（挂进当前助手消息的 part 序列——工具端点通过 traceId 关联当前 message-start 已开的消息），工具返回后 Dify 继续生成文本。前端无感：part 序列 text→data→text 自然交织。

### 5.2 生成类工具（generate_theme / generate_cases）

```
工具端点收到调用（不阻塞 Dify——立即返回"已受理"）：
1. 推 part(data): artifact-generated {status: in_progress}
2. 异步（生成专用线程池 generateExecutor）调 Dify 工作流（blocking，超时 300s）
   —— 材料解析**不在**这个池里：2026-09-21 起解析走独立的 parseExecutor，
   否则一次主题生成（5 个场景任务、单任务实测 150~600s）会把用户的上传解析排到十几分钟之后（07 §7.1）
3. schema 校验（fastjson2 + 自写校验器：8 字段/维度权重合计/引用完整性），失败重试 1 次
4. 成功：应用补丁到工作区 artifact → 推 part(data): artifact-generated{completed}
   （generate_cases 逐场景：每场景完成即推 case-generated，不等全部）
5. 失败：推事件带 error，编排智能体下轮从工具返回值感知失败并向用户解释
```

**事件落库规则（2026-09-21 修订）**：`AssistantEventPublisher` 有三种落点——
① traceId 对应的轮次还开着：事件并入该轮助手消息，随该轮一次性落库；
② 轮次已结束的结果类事件（artifact-generated 的 completed/failed、case-generated、parse-file）：新开一个短轮次广播**并**落一条助手消息，保证多端实时可见、历史可重放；
③ 中间进度事件（artifact-generated 的 in_progress，走 `pushTransient`）：轮次已结束时**只广播、不落库**。
原因：一次主题生成有 2~3 个节点进度，按 ② 会在消息流里堆出十几条"只含一张进度卡"的助手消息；前端把它们归并成一张卡后其余消息被清空，聊天框于是出现成排"只有头像、没有输出"的空气泡，刷新后按历史重放还会再复现一次（取证与修复见 07 §8）。

> 难点对策：Dify 工作流 300s 超时但 vllm Qwen3-30B 生成 15KB JSON 可能 2-5 分钟 → 工作流内**分场景拆块**（主题生成按"场景列表→画像冰山→维度"三段 LLM 串行，每段 <90s），DSL 里已按此设计。

### 5.3 确认落库（confirm action）

```
1. 幂等检查（artifact.status=confirmed 且内容 hash 未变 → 直接回 save-success）
2. 事务：artifact→confirmed；翻译落库（scenarios/维度展开/画像/案例/材料/冗余同步；先删当前版本旧行再插——覆盖语义）
3. 推 save-success {id, version, ex_id: themeId}
4. 前端提示成功；详情页数据即刻可见
```

### 5.4 发布初始化（publish）

```
POST publish（校验顺序：有 confirmed 内容 → 当前版本案例数≥1 → 状态=草稿或已发布）：
0. 案例数为 0：直接拒绝「请先在 AI 助手中生成并确认实战案例」。不得先抢占 status=1，也不得升版本。
1. status=1 发布中（复用现有枚举），落 act_theme
2. 提交异步任务（publishExecutor，并发 2）。每个案例写一行 act_drill_script：
   把已确认案例 JSON 原样写入 compiled_payload。内容来自案例生成，发布时不新调模型，也不再把案例、场景、维度拼成另一份 runtime。
   写入成功，该案例 status=compiled；失败则该案例记失败。
3. 全部案例成功：status=3 已发布 + 建 act_theme_version 新版本（复制）+ current_version_no 指向 + 冗余同步
4. 失败：保持 status=1；进度接口暴露 failed 案例数；retry 只重做失败案例
GET script-progress：{total: 当前版本案例数, completed, failed, progress, status}
```

> 2026-10-27 二次更正：线上每个案例在生成时就有 Markdown 和结构化 JSON 两份正文，学员开练用这两份，发布不另编第三份。本地案例生成只产出一份 JSON，所以发布只落这一份。9 月进度是案例数 × 2，10 月这次 3 案例 total=9，倍数对不上，进度不写死倍数，按实际落库的案例数计。完成横幅用场景数。

### 5.5 会话恢复与上下文拼装

```
重进会话：
1. GET messages（cursor 分页）渲染历史（data 块按 bizType 重放为 UI 卡片）
2. GET artifact（工作区 or confirmed 最新）渲染右面板
3. WS 连接后自动发 common-session-start（params.projectId=themeId）
上下文拼装（每次进 Dify）：
  system: 编排提示词
  inputs: {artifact_json: 当前工作区 artifact 摘要（场景名列表+维度名+计数，非全量15KB）,
           material_summary: 材料摘要,
           theme_status: 草稿/已发布}
  conversation_id: act_ai_session.dify_conversation_id（首轮返回后回存）
```

> 上下文瘦身：15KB 全量 JSON 每轮进 prompt 会挤爆上下文且贵。artifact_json 传"结构摘要"（场景名/画像类型/维度名+权重），生成类工具走 Java 侧传全量给工作流。

## 8. 关键实现难点与对策

| 难点 | 对策 |
|------|------|
| 15KB JSON 生成超时/格式崩坏 | 工作流分三段 LLM 串行（各<90s）；Java schema 校验+重试 1 次；Qwen3-30B 打样先行（交付前用真实材料跑一遍三工作流） |
| 工具回调与 WS 推送的关联 | 工具端点带 traceId 参数（DSL 工具定义里透传），WsFrameEncoder 按 traceId 找到当前打开的助手消息 part 上下文 |
| data part 流式 JSON 拼接 | 前端只在 part-end 解析；后端翻译器保证单个 data part 的 JSON 完整性（一次事件一个 part） |
| 两端同时在线 | WsSessionRegistry 多 Session 广播；消息落库为准，WS 仅实时 |
| **慢帧占住 WS 读线程 → 心跳误杀连接**（2026-09-21 实测） | 读线程只处理 pong，业务帧交 `WsInboundDispatcher` 按会话分道异步执行（道内串行保帧序）；单会话排队上限拒收，不无界堆内存 |
| **一次性推送的事件丢帧 → 前端卡片永久转圈**（2026-09-21） | 完成态判据落库（材料行只在提取成功后写入），前端按会话轮询 `GET /sessions/{id}/materials` 做兜底校正；解析失败（不写行）走"确认超时"终态收口，两条路径都不留转圈态 |
| **解析与生成共用线程池 → 上传解析被排到十几分钟后**（2026-09-21） | 解析独立 `parseExecutor`；同时把 generatePool 的 queue/max 语义列为待办（queue=64 使 max=4 永远不可达，等价 2 槽），本轮未改（需用户确认容量） |
| **进度事件逐条落库 → 聊天框成排空气泡**（2026-09-21 实测） | 源头：in_progress 改 `pushTransient`（只广播不落库）；前端：事件块被归并掉后回收已无内容且不在流式的消息（`dropEventBlock`），渲染层再过滤一道 0 块消息 |
