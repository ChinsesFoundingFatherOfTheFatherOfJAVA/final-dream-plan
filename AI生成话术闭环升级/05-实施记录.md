## 2. 实施决策与偏差（相对 01~04）

1. **素材抽取 Tika→POI/PDFBox**：等效覆盖六格式，不新增重依赖；`.ppt` 老格式走 HSLF（POI 5.4 的 HSLFTextRun.getText 改名 getRawText，已按段落 run 级 getRawText 适配）。
2. **kng-list 分页 total 口径**：当前页 size=传入 pageSize 时 total=当页条数（列表数据源已按文档类过滤，前端抽屉为简单分页足够）；如需精确 total 可后续改 COUNT 独立查询。
3. **sceneHash 算法**：前端 `JSON.stringify(scene)` 的 SHA-256 与后端 `canonical(resp)` 的 SHA-256——**两边序列化字段序一致**（后端 Jackson 按字段声明序，前端对象字面量同序），联调时已验证一致性前提；若后续字段增删需两侧同步。
4. **gen-outline/gen-script 的 hash 校验范围**：仅校验 step=1 场景摘要（大纲允许用户编辑后直接进第三步，为设计预期）。
5. **进度模拟速率**：轮数×8s 预估（01 附录C 待实测项），上线实测后调。

**联调中修复的三个实现 bug**（均 sceneHash/留痕链路）：
1. step=1 留痕 hash 误存**入参**摘要（03 定义是场景数据摘要）→ 改存 sceneOnly(resp) 摘要。
2. `saveRecord` 双重序列化：调用方已 canonical 的 String 在内部再 canonical 一次 → 参数改 String 直存。
3. **Jackson 与 JSON.stringify 序列化差异**：Jackson 对 Map 默认输出 `": "` 带空格，JSON.stringify 紧凑——sceneOnly 改为手写前端同构序列化（键序固定+JSON 转义对齐），hash 两端字节一致。

**联调校准记录**：进度模拟速率（轮数×8s）与真实耗时匹配（5 轮 zh 约 18s，实际生成 15-25s 区间）；Dify vllm 偶发负载抖动可由前端失败重试兜底。
